# CycleTLS 3.0.1: what each subagent researched and implemented

This branch (`version/3.0.1`) starts from `version/3.0.0` and adds fixes and opt-in features found by comparing CycleTLS with its upstream libraries, with peer projects, and with its own backlog. The work was split across subagents. This file records what each one did, in its own words where it wrote a section, and how the pieces were put together.

No default fingerprint changes in 3.0.1. Every new fingerprint feature is opt-in.

## New options at a glance

All are request options, spelled the same in the Node clients and in Go JSON. Go field names are in the agent sections.

| Option | Type | Effect |
|---|---|---|
| `tlsProfile` | string | Use a named utls ClientHello, for example `"chrome_133"`. 39 names; `TLSProfileNames()` lists them. |
| `shuffleExtensions` | boolean | Random TLS extension order per connection on the default-Chrome, `tlsProfile` and `ja4r` paths. |
| `clientHello` | string (hex) | Replay a captured ClientHello record. |
| `sessionResumption` | boolean | Resume TLS sessions (TLS 1.3 PSK, TLS 1.2 tickets). Resumed hellos carry extension 41. |
| `certPins` | string[] | Now enforced. 64 hex characters = SHA-256 of the certificate; `sha256/<base64>` = SHA-256 of its public key info. |
| `caCerts` | string[] (PEM) | Extra root CAs, added to the system roots. |
| `http2Priority` | `{weight, exclusive, streamDep}` or `false` | Priority fields of the HTTP/2 HEADERS frame. Weight is 1 to 256. |
| `proxyHeaders` | object | Extra headers on the CONNECT request to an HTTP or HTTPS proxy. |
| `readTimeout` (legacy client) | number (ms) | Fails a request whose body stalls. |
| `startupTimeout` (default client) | number (ms) | How long to wait for the Go process to start. Default 20000. |

Precedence for the ClientHello: `clientHello`, then `tlsProfile`, then `ja3`, then `ja4r`, then the User-Agent default.

`http2Fingerprint` now accepts the full Akamai form `SETTINGS|WINDOW_UPDATE|PRIORITY|PSEUDO_HEADER_ORDER`, and all four parts reach the wire.

Environment: `CYCLETLS_DEBUG=1` turns the Go debug log back on.

## Behaviour changes

These change what an existing caller sees. Each is explained in the section of the agent that made it.

- `proxy` with `forceHTTP3` returns an error. Before, the request went out directly, without the proxy.
- `certPins` is enforced. With HTTP/3, plain `http://` or a WebSocket request it returns an error, because those paths cannot check pins.
- An `http2Fingerprint` with a bad pseudo-header part or malformed settings is an error. Before, it was ignored.
- `quicFingerprint` no longer changes the TCP ClientHello. It has no effect in 3.0.1.
- `enableConnectionReuse` left out of a JSON request now means `true`. Go callers of `Do` keep the struct zero value.
- WebSocket requests honour `proxy`, `userAgent` and `cookies`. A refused proxy tunnel fails the request.
- An upstream WebSocket is no longer closed after 30 seconds of silence. A quiet upstream gets a ping; it is closed after 90 seconds with no traffic at all.
- A request with a bad proxy URL, URL or method fails by itself. Before, it ended the Go process.
- Go debug lines are off unless `CYCLETLS_DEBUG` is set.
- Go `Do` decodes `gzip, br` and zstd, and drops `Content-Encoding` and `Content-Length` from a decoded response.
- `GenerateJA4` returns the standard JA4 format and is deprecated in favour of `JA4FromClientHello`.
- Legacy Node client: init failures reject with `Error` objects; requests in flight reject when the Go process dies; non-string header values are coerced or rejected; `timeout: -1` means no timeout.
- Default Node client: `ws()` and `sse()` forward every option; `sse()` sends the caller's method and body; `close()` resolves after the child has exited; an invalid `port` throws; `port: 0` picks a free port.

## Research agents

The research agents changed no code. Their full reports are not in the repository; the findings that led to work are summarised here.

### research-utls

Compared CycleTLS's use of utls with upstream. It ran probes in scratch copies.

- The pinned utls v1.8.2 is the newest release. Upstream master is 184 commits ahead, untagged, and needs Go 1.27. A trial bump built and passed the spec tests but would move the Firefox default from 120 to 148 without notice. Not bumped.
- The JA4R path sent empty bodies for seven extension IDs, two of them invalid TLS. Implemented by impl-tls-spec.
- No session cache existed, so no connection ever resumed. A prototype resumed against three public sites. Implemented by impl-tls-handshake.
- `ShuffleChromeTLSExtensions`, `UTLSIdToSpec` (named parrots) and `Fingerprinter` (ClientHello import) exist in v1.8.2 and were unused. Implemented by impl-tls-spec.
- JA3 IDs 15 and 30031 hit the "not supported" error; 17 and 30032 had wrong bodies. Implemented by impl-tls-spec.
- `GenerateJA4` was not the standard algorithm. Replaced by impl-tls-spec.
- Left for later: the JA3 path sends Firefox signature algorithms under a Chrome User-Agent (fixing it changes JA4 for current users); real ECH (needs a DNS lookup and retry handling); certificate compression beyond brotli; GREASE on the JA4R path.

### research-h2h3

Read the fhttp fork, quic-go and uquic, and ran the HTTP/2 parser.

- `proxy` with `forceHTTP3` connected directly. Fixed by impl-h2-h3-proxy.
- The Akamai `http2Fingerprint` string was misparsed: the README's own example sent no PRIORITY frames, and the pseudo-header part was dropped. Fixed by impl-h2-h3-proxy.
- `certPins` was accepted and never read. Fixed by impl-tls-handshake.
- `quicFingerprint` changed the TCP ClientHello and had no effect on QUIC. Taken off the TCP path by impl-h2-h3-proxy; wiring it to QUIC needs uquic's own HTTP/3 stack and is not done.
- WebSocket requests ignored `proxy` and carry no TLS fingerprint. The proxy half was fixed by impl-go-dispatch.
- A bad proxy URL called `log.Fatal`. Fixed by impl-go-dispatch.
- Left for later: refreshing the default HTTP/2 settings to current browsers (changes every user's wire output), client certificates, DNS overrides, local address binding, SOCKS5 UDP for HTTP/3, HTTP/3 fingerprints.

### research-gaps

Read every open issue and old pull request, the public API on both sides, and ran probe scripts against the built client.

- The default client stopped answering after about 240 requests because nothing read the Go process's stdout. Fixed on both sides by impl-node-v2 and impl-go-dispatch.
- A WebSocket silent for 30 seconds was destroyed, and the legacy path panicked the Go process. Fixed by impl-go-dispatch.
- One request with a numeric header value timed out and so did every later request on that client. Fixed by impl-go-dispatch and impl-node-legacy.
- A request over 64 KB threw an uncaught exception in the default client. Fixed by impl-node-v2.
- The legacy client never noticed the Go process exiting. Fixed by impl-node-legacy.
- V2 SSE dropped the caller's headers; `enableConnectionReuse` read as false when left out; Go `Do` dropped `ServerName`, `DisableGrease` and `TLS13AutoRetry`. Fixed by impl-go-dispatch.
- A stale `tests/test-utils.js` shadowed the TypeScript file, which is why five Jest suites failed. Fixed by impl-node-legacy.
- Not fixed: the shipped binary is built from `src/index.go`, so the WebSocket auth token, rate limiter and concurrency cap in `cycletls/index.go` are never switched on. Turning the token on needs the Go entry point and both Node clients changed together.
- Old pull requests 379 (protocol version in the response), 360 (redirect hook) and 358 (client certificates) are not on this branch and would need redoing against the new files.

### research-peers

Compared user-facing features with nine other libraries and captured a real Chrome 157 ClientHello. It started two helper agents for part of the reading.

- CycleTLS is the only one of these with JA4R input and a server-sent-events API.
- Peers that have named presets, random extension order, ClientHello import, enforced pinning, CONNECT headers or an Akamai string: these are the features added in 3.0.1.
- The Go default ClientHello matches Chrome 133: it has no trust-anchors extension, no ML-DSA signature algorithms and a fixed extension order. Real Chrome 157 has all three. The legacy Node default pairs an old Firefox JA3 with a Chrome 101 User-Agent and matches no browser. Not changed in 3.0.1, because it changes every user's wire output.
- Peers ship newer presets than utls v1.8.2 can provide: Chrome 152 to 157 and Firefox 148 to 158. `tlsProfile` stops at Chrome 133.
- Left for later: default header sets per browser, request retries, response metadata (protocol, remote address, timings), local address binding, IPv4-only dialing, cookie dump and restore.

## Implementation agents

Each section below was written by the agent that did the work, on its own branch, and is included unchanged apart from heading levels.

### impl-tls-spec: TLS ClientHello changes

utls stays at v1.8.2. Everything here uses what that version already ships.

Three options are new, all off by default:

| Go (`Options` / `Browser`) | JSON | Type | What it does |
|---|---|---|---|
| `TLSProfile` | `tlsProfile` | `string` | Send the ClientHello of a named utls profile |
| `ShuffleExtensions` | `shuffleExtensions` | `bool` | Random extension order on each connection |
| `ClientHello` | `clientHello` | `string` | Replay a captured ClientHello given as hex |

Which option decides the ClientHello, first match wins:

1. `clientHello`
2. `tlsProfile`
3. `quicFingerprint`
4. `ja3`
5. `ja4r`
6. the User-Agent default (Chrome spec, or utls Firefox for a Firefox User-Agent)

So `tlsProfile` and `clientHello` override `ja3` and `ja4r` when both are set. Nothing is merged: the losing options are ignored for TLS.

The tests for all of this are Go unit tests in `cycletls/` that need no network. They build the ClientHello with a utls `UClient` on an in-memory pipe, or send it to an `httptest` TLS server on 127.0.0.1 that records what it receives, and read the result with the new JA3/JA4 helpers.

#### 1. JA4R path sent empty extension bodies

**What was missing.** `CreateExtensionFromID` (`cycletls/extensions.go`) had no case for 0x0011, 0x0015, 0x0018, 0x0029, 0x002c, 0x0032 and 0x0039, so each became `GenericExtension{Id, Data: []}`. Run against the old code, the new tests reported:

```
extension 0x0011 has a zero-length body
extension 0x0018 has a zero-length body
extension 0x002c has a zero-length body
extension 0x0032 has a zero-length body
pre_shared_key is extension 8 of 11, want last
pre_shared_key has a zero-length body
```

An empty `signature_algorithms_cert` and a `pre_shared_key` that is empty or not last are invalid TLS. The JA3 path already had valid bodies for the same IDs in `genMap`.

**What changed.**

- `CreateExtensionFromID`: before falling back to an empty generic extension, it looks the ID up in `genMap`. That covers 0x0011 (`StatusRequestV2Extension`), 0x0018 (`FakeTokenBindingExtension`), 0x0029 (`UtlsPreSharedKeyExtension`), 0x002c (`CookieExtension`), 0x0032 (`SignatureAlgorithmsCertExtension`), 0x0039 (`QUICTransportParametersExtension`), and also 15, 13172, 30031 and 30032.
- 0x0015 is a `UtlsPaddingExtension` with the new `ja4rPaddingStyle`: the BoringSSL length when the unpadded hello is 256 to 511 bytes, one zero byte otherwise. BoringSSL sends no padding extension outside that range, but a JA4_r that lists 0x0015 counts and hashes it, so it is always sent.
- `JA4RStringToSpec` (`cycletls/utils.go`) calls the new `movePreSharedKeyLast`. JA4_r sorts extensions by ID, which put 0x0029 mid-list.

**JA4.** The IDs on the wire are the same as before, so the JA4 is the same. The one exception is 0x0029: with no session to resume there are no identities or binders to send, and utls leaves the extension out (`Config.OmitEmptyPsk`, which `dialTLS` sets). A JA4_r string that lists 0029 therefore produces a hello with one extension fewer than the string says. Before this change the hello carried `00290000`, which matched the count and was not valid TLS.

**Tests** (`cycletls/extension_bodies_test.go`): `TestJA4RExtensionBodiesAreNotEmpty` checks each body is non-empty, that 0x0011 is `000702000400000000`, that padding is zero bytes, and that the JA4 of the hello equals the JA4 of the input string. `TestJA4RPreSharedKeyIsLastOrAbsent` checks 0x0029 is last or absent and every other ID is still sent. Both failed before the change with the output above.

**Left out.**

- 0x0039 (`quic_transport_parameters`) is now the utls type but still has an empty parameter list. That is a well-formed encoding, and the extension has no meaning on a TCP connection whatever its body.
- 0x002c (`cookie`) is sent as an empty cookie (`0000`). A cookie belongs in the reply to a HelloRetryRequest, so there is no right value for a first hello.
- The hand-written delegated credentials body (0x0022, two algorithms where Firefox sends four) and `case 0x6399`, which treats a key-exchange group as an extension ID, are unchanged. Both were outside this item.
- The JA4R path still adds no GREASE (gap 11 in the research report). That changes bytes for every JA4R user and needs its own changelog line.

#### 2. More JA3 extension IDs

**What was missing.** `StringToSpec` returns an error for any ID not in `genMap`. 15 and 30031 were not there. 17 was sent with an empty body and 30032 with one zero byte, which no client sends. Before the change `TestJA3ExtensionIDs` and `TestJA3NewExtensionIDsOneByOne` failed in `StringToSpec` with "Extension {{ 15 }} is not Supported".

**What changed** (`genMap` in `cycletls/utils.go`):

| ID | Before | Now | Body |
|---|---|---|---|
| 15 heartbeat | error | `GenericExtension{15, 01}` | `01` |
| 30031 channel_id (old) | error | `FakeChannelIDExtension{OldExtensionID: true}` | empty |
| 17 status_request_v2 | empty generic | `StatusRequestV2Extension{}` | `000702000400000000` |
| 30032 channel_id | generic, body `00` | `FakeChannelIDExtension{}` | empty |

17 and 30032 change bytes for JA3 strings that contain them. JA3 and JA4 hashes do not change, since neither covers extension bodies.

`supportedSignatureAlgorithmsExtensions` in `extensions.go` is removed. Its keys were names (`"PKCS1WithSHA256"`, `"rsa_pkcs1_sha256"`) and the only lookup used `fmt.Sprintf("0x%04x", rawSig)`, so no lookup could match; the raw-value fallback did the work and still does.

**Tests** (`cycletls/extension_bodies_test.go`): the JA3 read back from the hello equals the input string, which fixes each ID's position; bodies are compared byte for byte; 15 and 30031 are each tried first, in the middle and last; extension 42 is still refused.

**Left out.** 17613 stays a `GenericExtension`. `utls.ApplicationSettingsExtensionNew` writes the same five bytes, but `cycletls/tests/unit/issue427_test.go` asserts the generic type and that directory is not mine to edit. IDs with no known valid body (42, 47, 14, 58, 65486) still return the error.

#### 3. Named TLS profiles: `tlsProfile`

**What was missing.** The only use of a utls parrot was `HelloFirefox_Auto` for a Firefox User-Agent with no fingerprint. A JA3 string cannot carry signature algorithms, key shares, supported versions, certificate compression, ALPS or padding; a utls profile carries all of them.

**What changed** (new file `cycletls/tls_profiles.go`):

- `TLSProfileNames() []string` returns the accepted names, sorted.
- `TLSProfileToSpec(name string, forceHTTP1 bool) (*utls.ClientHelloSpec, error)` maps the name to a `utls.ClientHelloID`, calls `utls.UTLSIdToSpec`, and applies the forceHTTP1 filter. An unknown name returns `unknown tlsProfile "x"; valid names: ...` with the full list. Names are matched in lower case with `.`, `-` and spaces read as `_`, so `Safari_16.0` works.
- `applyForceHTTP1` is the ALPN/ALPS filter that used to be inline in `ModernChromeSpec`, which now calls it.

The 39 names: `chrome`, `chrome_58`, `chrome_62`, `chrome_70`, `chrome_72`, `chrome_83`, `chrome_87`, `chrome_96`, `chrome_100`, `chrome_102`, `chrome_106`, `chrome_115_pq`, `chrome_120`, `chrome_120_pq`, `chrome_131`, `chrome_133`, `firefox`, `firefox_55`, `firefox_56`, `firefox_63`, `firefox_65`, `firefox_99`, `firefox_102`, `firefox_105`, `firefox_120`, `safari`, `safari_16_0`, `ios`, `ios_11_1`, `ios_12_1`, `ios_13`, `ios_14`, `edge`, `edge_85`, `edge_106`, `android_11_okhttp`, `360_7_5`, `360_11_0`, `qq_11_1`. The unversioned names follow the utls "Auto" IDs (today Chrome 133, Firefox 120, Safari 16.0, iOS 14, Edge 85) and will move when utls is upgraded.

```go
resp, err := client.Do("https://example.com", cycletls.Options{
    TLSProfile: "chrome_133",
    UserAgent:  "Mozilla/5.0 ... Chrome/133.0.0.0 Safari/537.36",
}, "GET")
```

```json
{ "url": "https://example.com", "tlsProfile": "firefox_120", "userAgent": "Mozilla/5.0 ... Firefox/120.0" }
```

A profile covers the TLS ClientHello only. HTTP/2 settings, pseudo-header order, header order and the User-Agent still come from `http2Fingerprint`, `headerOrder` and `userAgent`; set them to match the profile.

**Tests** (`cycletls/tls_spec_options_test.go`): `TestTLSProfilesHandshakeAndMatchUTLS` runs every name: it completes a handshake with the local server, then compares the JA4 and JA3 of the hello the server received with a hello utls builds from the same `ClientHelloID`. For profiles that shuffle (Chrome 106 and later) the JA3 comparison sorts the extension list. Padding is left out of both sides: BoringSSL-style padding depends on the hello length and the Chrome GREASE ECH extension has a random length, so two hellos from one utls spec can differ in whether they carry it. Other tests cover the name list and error text, forceHTTP1, a real request through `newRoundTripper` for three profiles with `ja3` and `ja4r` also set, and the error for an unknown name.

**Left out.**

- The PSK parrots (`HelloChrome_100_PSK`, `112_PSK_Shuf`, `114_Padding_PSK_Shuf`, `115_PQ_PSK`): without a session cache they send no PSK, so they would be duplicates of the plain profiles under a misleading name.
- `HelloRandomized*`: the research probe saw one of two handshakes fail.
- Chrome 155, Firefox 148 and Safari 26.3 exist only on untagged utls master, which needs Go 1.27.
- No HTTP/2 defaults per profile.
- HTTP/3 is not affected by the option.

#### 4. Extension-order shuffle: `shuffleExtensions`

**What was missing.** `ModernChromeSpec` has one fixed extension order and the JA4R path sends extensions sorted by ID. Chrome has sent a new random order on every connection since version 106.

**What changed.** With `shuffleExtensions: true`, `shuffleSpecExtensions` (`cycletls/tls_profiles.go`) calls `utls.ShuffleChromeTLSExtensions` on the spec. GREASE, padding and pre_shared_key keep their positions. It applies on three paths:

- the default Chrome spec and the `ja4r` path, in `roundTripper.dialTLS`;
- a `tlsProfile`, in `roundTripper.optInSpec`.

It does nothing with an explicit `ja3` or an imported `clientHello`, where the caller gave the order, nor on the Firefox default path, since Firefox does not shuffle. The JA3 hash changes on every connection when this is on, as it does for Chrome. JA4 does not, because JA4 sorts.

```go
cycletls.Options{ShuffleExtensions: true, UserAgent: chromeUA}
```

```json
{ "url": "https://example.com", "ja4r": "t13d1516h2_...", "shuffleExtensions": true }
```

**Tests** (`TestShuffleExtensions`): each path sends real requests to the local server. With the option off, four hellos have the same order. With it on, six hellos have at least two different orders, the same extension set and the same JA4, and on the Chrome path GREASE stays first and last. With `ja3` set and the option on, the JA3 on the wire equals the input four times running; an imported hello keeps its order too.

**Left out.** Shuffling on by default for Chrome User-Agents. It would change the JA3 of every default-path user.

#### 5. ClientHello importer: `clientHello`

**What was missing.** `utls.Fingerprinter` was not used anywhere, so there was no way to copy a client that JA3 or JA4_r cannot describe.

**What changed** (new file `cycletls/clienthello_import.go`): `ClientHelloToSpec(clientHelloHex string, forceHTTP1 bool) (*utls.ClientHelloSpec, error)`.

- Input is the hex of the TLS record as captured (`16 03 01 ...`) or of the bare handshake message (`01 ...`). Upper or lower case, an optional `0x`, and spaces, newlines or `:` between bytes are accepted. A hello split across several records is joined.
- It runs `utls.Fingerprinter{AllowBluntMimicry: true}.FingerprintClientHello`, so extensions utls has no type for are replayed byte for byte.
- The captured server name is not kept: the SNI extension stays and utls fills in the host of each connection.
- A captured `pre_shared_key` is dropped. Its ticket and binder belong to another session.
- utls discards captured key shares and makes new ones, and GREASE values are redrawn per connection.
- Bad hex returns `clientHello: not valid hex: ...`; a record that is not a ClientHello or is cut short returns an error that also starts with `clientHello:`.

```go
cycletls.Options{ClientHello: "16030106b2010006ae0303...", UserAgent: ua}
```

```json
{ "url": "https://example.com", "clientHello": "16030106b2010006ae0303..." }
```

**Tests**: `TestClientHelloImportRoundTrip` takes hellos produced by this code (default Chrome, `firefox_120`, `safari_16_0`, a JA3 with 15, 17 and 30031), imports each in four input forms, rebuilds, and checks JA3, JA4, JA4_r, ALPN and the bodies of the extensions that hold no per-connection value; the imported spec then completes a handshake with the local server. Further tests: the captured SNI is replaced, an appended `pre_shared_key` is dropped, forceHTTP1 works, five kinds of bad input return an error, and a real request with `clientHello`, `tlsProfile` and `ja3` all set sends the imported hello.

**Left out.** Base64 input, the tlsfingerprint.io JSON format (`UnmarshalJSONClientHello`), and real PSK resumption from a capture (`RealPSKResumption`), which needs a session cache. The padding extension of a capture pads to the captured hello length, which is what utls does.

#### 6. JA3 and JA4 of a ClientHello

**What was missing.** `GenerateJA4` (`cycletls/ja4.go`) was not the FoxIO algorithm: no cipher or extension counts, no ALPN characters, hashes cut to 1 and 4 hex characters, HTTP headers and the User-Agent mixed in. A search of every `.go` file found no caller. Tests had to ask tls.peet.ws what was sent.

**What changed** (new file `cycletls/clienthello_fingerprint.go`):

- `ParseClientHello(raw []byte) (*ClientHelloInfo, error)` reads TLS records or a bare handshake message.
- `ClientHelloInfo` has methods `JA3()`, `JA3Hash()`, `JA4()`, `JA4R()` and `ExtensionBody(id)`.
- `JA3FromClientHello(raw) (ja3, hash string, err error)`, `JA4FromClientHello(raw) (string, error)`, `JA4RFromClientHello(raw) (string, error)`.

JA4 follows the FoxIO rules: version from `supported_versions` when present, `d` or `i` for SNI, counts without GREASE and capped at 99, first and last character of the first ALPN value (`00` when there is none, hex digits when not alphanumeric), sorted lists, SNI and ALPN counted but not hashed, signature algorithms in wire order, 12 hex characters per hash.

`GenerateJA4` keeps its signature and now returns the FoxIO format for what it is given. Its arguments carry no ALPN list and no signature algorithms, so the ALPN part is `00` and the last hash covers extension IDs only; `headers` and `userAgent` are ignored. It is marked deprecated in favour of `JA4FromClientHello`. Its unused helpers `getTLSVersionString`, `hashCipherSuites` and `hashExtensions` are gone. `GenerateJA4HTTP` and `GenerateJA4H2` are unchanged.

```go
uconn.BuildHandshakeState()
ja4, err := cycletls.JA4FromClientHello(uconn.HandshakeState.Hello.Raw)
```

**Tests** (`cycletls/clienthello_fingerprint_test.go`): `TestJA4MatchesFoxIOExample` reproduces the Chrome example from the FoxIO spec, `t13d1516h2_8daaf6152771_e5627efa2ab1`, and its JA4_r. Others cover the prefix rules, a hello built by utls from a known spec (as a message, one record, and split records), truncated input, and `GenerateJA4`.

**Left out.** `GenerateJA4`'s output changed. Any Go caller that stored the old string will see a different one; the old one was not a JA4. The fingerprint is not added to the response. JA4 for QUIC (`q` prefix) and JA4H are not covered. `GenerateJA4HTTP` is also not the FoxIO JA4H; it was outside this item.

That function was outside the files this change could touch.

### impl-tls-handshake: TLS handshake options

Five changes to the TCP TLS handshake in `cycletls/roundtripper.go` (`dialTLS` and its two retry dials). The new code is in `cycletls/tls_handshake.go`, `cycletls/cert_pinning.go` and `cycletls/session_cache.go`; the tests are in `cycletls/tls_handshake_test.go`. utls stays at v1.8.2.

| Option (JSON) | Go field (`Options` and `Browser`) | Type | Default |
|---|---|---|---|
| `sessionResumption` | `SessionResumption` | `bool` | `false` |
| `certPins` | `CertPins` | `[]string` | none |
| `caCerts` | `CACerts` | `[]string` | none |

All tests run against local servers (`httptest`, `tls.Listen`) with a CA generated in the test. None uses the network.

#### 1. TLS session resumption (`sessionResumption`)

**What was missing.** The three `utls.Config` literals in `roundtripper.go` (first dial and both retries) set `ServerName`, `OmitEmptyPsk` and `InsecureSkipVerify` and nothing else. No `ClientSessionCache` existed anywhere in non-test code, so every connection was a full handshake. A JA3 that lists extension 41 (`pre_shared_key`) never produced it: with no session to offer, utls drops the extension.

**What changed.** With `sessionResumption: true`:

- `handshakeConfig` (`tls_handshake.go`) sets `ClientSessionCache` and `PreferSkipResumptionOnNilExtension: true`. Without the second flag utls panics on a spec that has neither a session-ticket nor a pre-shared-key extension.
- `finishHandshakeSpec` calls `ensurePreSharedKeyLast`, which appends `&utls.UtlsPreSharedKeyExtension{}` as the last extension when the spec has none, and moves an existing one to the end. utls keeps it off the wire while there is no session (`OmitEmptyPsk`), so the first hello to a host is byte-for-byte what it was. A resumed TLS 1.3 hello is the same list plus 41 at the end.
- A spec that offers TLS 1.2 only (a `771,` JA3 without `tls13AutoRetry`) resumes with its session ticket, extension 35. Extension 41 never appears there.

It is off by default because a resumed hello carries extension 41, so its JA3 and JA4 differ from the first hello's. Real browsers behave the same way.

**Where the cache lives.** With connection reuse off, `createNewClient` builds a new `roundTripper` for every request. A cache on the roundTripper would always be empty, and the client pool is skipped in that case too. So the caches sit in a package-level registry (`sessionCaches` in `session_cache.go`), and `createNewClient` hands the right one to the roundTripper through the unexported `Browser.sessionCache`.

The registry key (`sessionCacheKey`) is `generateClientKey` with cookies, header order, HTTP/2 fingerprint, timeout and redirect policy blanked. What is left decides whether two requests may share a session: JA3/JA4R/QUIC fingerprint, user agent, SNI, proxy, `insecureSkipVerify`, `forceHTTP1`, `certPins`, `caCerts`. A session is never offered through a different proxy or under a different fingerprint. A field added to `generateClientKey` later is covered without further work.

The registry holds at most 100 caches (least recently used goes first) and each cache holds 64 server names. A roundTripper built directly (`NewTransport` and the other constructors) gets its own cache, which lives as long as it does.

**Usage.**

```js
await client.get(url, { sessionResumption: true });
```

```go
client.Do(url, cycletls.Options{SessionResumption: true}, "GET")
```

**Tests.** `TestSessionResumption` runs two requests with reuse off against a server that reports `DidResume`, for the default Chrome hello on HTTP/2 and HTTP/1.1, a JA3 upgraded to TLS 1.3, a TLS 1.2 JA3, and the Firefox default. It checks that the second request resumed, that the second ClientHello has 41 as its last extension and is otherwise the first hello, and that with the option off neither hello has 41 and nothing resumes. `TestSessionResumptionKeepsFirstHello` compares the first hello with the option on and off. `TestSessionResumptionPerRoundTripper` covers the cache of a directly built roundTripper. `TestSessionResumptionConcurrent` runs 32 parallel requests on one cache under `-race`. `TestSessionCacheKey` checks which fields split the cache and that the registry stays bounded. `TestDoCarriesTLSHandshakeOptions` goes through `CycleTLS.Do`.

**Left out.**

- 0-RTT. utls v1.8.2 only sets early data on its QUIC path.
- Single-use tickets. Chrome uses a TLS 1.3 ticket once; this cache, like Go's, offers the newest ticket until the server sends another.
- HTTP/3 and WebSocket. Neither goes through `dialTLS`.
- The cache key inside one cache is the SNI, as in utls and Go. Two servers reached under the same SNI on different ports share an entry; the server that did not issue the ticket ignores it and does a full handshake.
- Not run against a live site in this change. The research prototype did that with the same three settings.

#### 2. Certificate pinning (`certPins`)

**What was missing.** `Options.CertPins` was declared in `types.go` and read nowhere. A caller who set it got no check at all.

**What changed.** After every TLS handshake, `verifyHandshake` compares the certificates the server presented with the pins. If none matches, the connection is closed and the request fails with an error that wraps `ErrCertPinMismatch` and names the leaf's two pin values.

The field keeps its type (`[]string`). An entry has one of two forms, and the form says what was hashed:

| Form | Matches |
|---|---|
| 64 hex characters | SHA-256 of the whole certificate (DER). This is the meaning the field's comment and `CertPinConfig` already documented. |
| `sha256/<base64>` | SHA-256 of the certificate's SubjectPublicKeyInfo, the HPKP `pin-sha256` value. |

A hex pin is never compared with a key hash and a `sha256/` pin is never compared with a certificate hash. Hex entries are checked with the existing `CertPinConfig.Validate`. Any other entry, bare base64 included, fails the request before anything is dialed, with an error that names the entry.

Rules:

- Any certificate in the chain the server sent may match, so an intermediate can be pinned.
- The list applies to every TLS connection of the request, redirect hops to other hosts included. There is no per-host syntax.
- Pins are checked with `insecureSkipVerify` on as well. That flag turns off chain verification only.
- On a resumed session the pins are checked against the chain stored with the session.
- The check runs in `dialTLS` and in both retry dials before the connection is cached, so no HTTP/1.1 request and no HTTP/2 preface is written to a server that failed it. HTTP/2 connections are opened through the same function.
- With a proxy the pins apply to the target's certificate, not the proxy's.

Three paths cannot check pins, and each refuses the request (`checkTLSHandshakeOptions`, called at the top of `RoundTrip`, and `dispatchWebSocketRequest`):

- HTTP/3. The QUIC handshake is done by quic-go with its own TLS config. A `VerifyConnection` hook there could enforce the pins; that code belongs to the HTTP/3 work, so for now `certPins` with `forceHTTP3` returns an error.
- WebSocket. gorilla/websocket dials with `crypto/tls`.
- Plain `http://`, including a redirect from https to http. There is no certificate to check.

**Usage.**

```js
await client.get(url, {
  certPins: [
    "sha256/47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=", // SPKI
    "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855", // whole certificate
  ],
});
```

To get the values for a host:

```sh
# SPKI pin
openssl s_client -connect example.com:443 </dev/null 2>/dev/null \
  | openssl x509 -pubkey -noout | openssl pkey -pubin -outform der \
  | openssl dgst -sha256 -binary | base64
# certificate pin
openssl s_client -connect example.com:443 </dev/null 2>/dev/null \
  | openssl x509 -outform der | openssl dgst -sha256 -hex
```

**Tests.** `TestParseCertPin` covers the accepted and rejected forms. `TestCertPinFormsDoNotCross` checks that each form only matches its own hash. `TestCertPins` runs on HTTP/1.1 and HTTP/2: leaf and issuer pins in both forms pass; a wrong pin fails with `ErrCertPinMismatch` and the handler is never called; the same with `insecureSkipVerify`; and a resumed session is still checked. `TestCertPinMismatchSendsNoRequestBytes` uses a raw `tls.Listen` server that counts application bytes after the handshake: zero on both protocols. `TestCertPinsOnRetryDial` and `TestCustomSNIOnCurveRetry` cover both retry dials. `TestCertPinsRejectedWhereTheyCannotBeChecked` covers an invalid pin (the server sees no ClientHello), HTTP/3, WebSocket and plain http.

**Left out.** Enforcement on HTTP/3 and WebSocket (refused instead). Per-host pin lists. Backup-pin or expiry policy. `Browser.WebSocketConnect`, the Go-only WebSocket helper, still ignores pins.

#### 3. Custom root CAs (`caCerts`)

**What was missing.** The handshake config had no `RootCAs`, so only the system roots were trusted. A server signed by a private CA could only be reached with `insecureSkipVerify`.

**What changed.** `caCerts` is a list of PEM strings; one string may hold several certificates. `buildRootCAs` starts from the system pool and adds them, and `handshakeConfig` sets the result as `RootCAs` on the first dial and both retries. The system roots stay trusted.

Invalid input fails the request before anything is dialed, with an error that names the entry (`invalid caCerts[1]: ...`). `appendPEMCerts` is stricter than Go's `AppendCertsFromPEM`, which skips what it cannot read: text that is not PEM, a block that is not a `CERTIFICATE`, a certificate that does not parse, trailing text and an empty string are all errors.

The pool is also copied into the roundTripper's `TLSConfig` when the caller did not set roots there, because the HTTP/3 dials build their TLS config from that field. This part is inferred from reading `ConvertUtlsConfig` and `http3.go`; no HTTP/3 test runs it.

**Usage.**

```js
await client.get(url, { caCerts: [fs.readFileSync("corp-root.pem", "utf8")] });
```

**Tests.** `TestCACerts`, on HTTP/1.1 and HTTP/2: without the option the request fails verification and the handler is never called; another private CA does not help; with the right CA the request succeeds. `invalid_pem` covers six kinds of bad input and checks the server saw no ClientHello. `system_roots_kept` checks that the pool is more than the custom CA.

**Left out.** Client certificates (mTLS). A switch to trust only the given CAs. WebSocket does not use `caCerts`; it fails closed, as an untrusted certificate.

#### 4. Custom SNI dropped on retry

**What was missing.** `dialTLS` works out the SNI (`serverName`, the custom name when set) but passed `host` to `retryWithTLS13CompatibleCurves` and `retryWithOriginalTLS12JA3`, and both put it in `ServerName`. A request with `serverName` set sent the custom name on the first dial and the URL's host on the retry.

**What changed.** Both calls pass `serverName`, the parameter is renamed to match, and all three dials build their config with `handshakeConfig(serverName)`.

The curve retry's spec rebuild now sits in one function, `tls13RetrySpec` (`roundtripper.go`). It rebuilds from the QUIC fingerprint, the JA3, or the default Chrome JA3, as before. A new fingerprint source in the spec selection needs a case there, or the retry sends a different hello than the first dial.

**Tests.** `TestCustomSNIOnTLS12FallbackRetry`: a `771,` JA3 with `tls13AutoRetry` goes out upgraded to TLS 1.3; the server refuses the first handshake, which triggers the TLS 1.2 fallback dial. Its `GetConfigForClient` must see the custom name twice. Before the fix it saw `["custom.test", ""]`. `TestCustomSNIOnCurveRetry` covers the other retry. No JA3 or JA4_r string reaches the unsupported-curve error at utls v1.8.2, so the test's dialer makes the first connection fail with that error text at its first write; the retry then runs as in production.

#### 5. Firefox default path ignored `forceHTTP1`

**What was missing.** With a Firefox user agent and no fingerprint, `dialTLS` sets `helloID = utls.HelloFirefox_Auto` and no spec. The parrot's ALPN list (`h2`, `http/1.1`) went out unchanged, so `forceHTTP1` still negotiated HTTP/2.

**What changed.** Nothing in the spec-selection lines. `finishHandshakeSpec`, which runs after them, expands a built-in parrot into its spec with `utls.UTLSIdToSpec` when `forceHTTP1` (or `sessionResumption`) is on, and `forceHTTP1ALPN` sets ALPN to `http/1.1` and drops ALPS, the same rule as `ModernChromeSpec(true)`. utls applies a built-in parrot the same way, so the hello is otherwise identical. When neither option is on, the parrot is used untouched.

**Tests.** `TestFirefoxDefaultHonoursForceHTTP1`: with `forceHTTP1` the server sees ALPN `[http/1.1]` and serves HTTP/1.1; without it the hello still offers `[h2 http/1.1]` and negotiates HTTP/2.

#### Found on the way, not fixed

- A JA3 whose version token is not 769 to 772 (for example `773,...`), or is 769, panics inside utls `ApplyPreset`: `StringToSpec` ignores the error from `createTlsVersion` and puts a nil extension in the list (`utils.go`). Seen while probing for the curve retry.
- `go vet ./...` reports six "cancel function is not used on all paths" findings in `index.go` and `ws_handler_v2.go`. They predate this change.
- `dialTLS` does not close the raw connection when building the spec fails. The paths added here close it; the earlier returns in the spec-selection lines do not.
- `CycleTLS.Do` builds its `Browser` by hand and leaves out `ServerName`, `DisableGrease` and `TLS13AutoRetry`.

### impl-h2-h3-proxy: HTTP/2, HTTP/3 and proxy fixes

Six changes to the Go side of CycleTLS. Each section says what was wrong, what changed, how it is tested and what was left out. Paths are relative to `cycletls/`.

New options:

| JSON | Go (`Options` and `Browser`) | Type |
|---|---|---|
| `http2Priority` | `HTTP2Priority` | `*HTTP2PriorityOptions` |
| `proxyHeaders` | `ProxyHeaders` | `map[string]string` |

New exported names: `HTTP2PriorityOptions`, `ErrHTTP3ProxyUnsupported`, `HTTP2Fingerprint.PriorityFrames`, `HTTP2Fingerprint.NoPriorityFrames`, `HTTP2Fingerprint.PseudoHeaderOrder()`.

Every "failed before" below was run against the unchanged `version/3.0.1` code, not read off the source.

#### 1. Akamai-format `http2Fingerprint`

##### What was wrong

`NewHTTP2Fingerprint` read the third part of the string with `Sscanf("%d")` as a 0/1 flag and stored the fourth part without using it. The README's own example,

```
1:65536;4:131072;5:16384|12517377|3:0:0:201,5:0:0:101,7:0:0:1,9:0:7:1,11:0:3:1,13:0:0:241|m,p,a,s
```

parsed as "exclusive = true" (the leading `3`) and no PRIORITY frames. With a Chrome User-Agent the wire showed zero PRIORITY frames, first stream 1, pseudo-header order `m,a,s,p` and an exclusive HEADERS priority. The pseudo-header order always came from the User-Agent (`parseUserAgent` in `utils.go`), so a Safari string with a Chrome User-Agent still sent Chrome's order.

There was a second trap. With part 3 `0` and a Firefox User-Agent, fhttp wrote Firefox's six legacy PRIORITY frames anyway and opened stream 15, because `AutoWriteFrames` falls back to the browser preset when `PriorityFrames` is nil. Current Firefox sends no PRIORITY frames.

##### What changed

`http2.go`: `NewHTTP2Fingerprint`, `parsePriorityEntry`, `pseudoHeaderOrder`, `HTTP2Fingerprint.PseudoHeaderOrder`, `String`, `Apply`, and three `roundTripper` methods: `parsedHTTP2Fingerprint`, `configureHTTP2Transport`, `applyPseudoHeaderOrder`.

Accepted grammar:

```
fingerprint = settings "|" window "|" priority "|" pseudo
settings    = id ":" value *( ("," / ";") id ":" value )   ; id 0-65535, value 0-4294967295
window      = 0-4294967295                                  ; connection WINDOW_UPDATE increment
priority    = "0"                                           ; no PRIORITY frames
            / "1"                                           ; 3.0.0 meaning, see below
            / entry *( "," entry )
entry       = streamID ":" exclusive ":" dependsOn ":" weight
              ; streamID 1 to 2^31-1, exclusive 0 or 1, dependsOn 0 to 2^31-1, weight 1-256
pseudo      = ""                                            ; keep the User-Agent's order
            / a permutation of m,a,s,p                      ; :method :authority :scheme :path
```

- **Settings** take `,` or `;`, also mixed. tls-client and tls.peet.ws print `;`, azuretls prints `,`. Any setting ID is sent, known or not.
- **Priority entries** fill `HTTP2Settings.PriorityFrames` in fhttp. Weight in the string is the RFC 7540 weight (1-256); the wire byte is weight minus one, the same convention azuretls and tls.peet.ws use. The first request goes out on the stream after the last entry (13 gives 15).
- **`0`** means no PRIORITY frames, for every User-Agent. For a Firefox User-Agent `Apply` sets the transport's `Navigator` to Chrome. That is the only way to make this fhttp version write no PRIORITY frames and open stream 1; an empty frame list would open stream 0. SETTINGS and WINDOW_UPDATE still come from the string, so nothing else on the wire changes. One side effect: fhttp then caps response headers at 262144 bytes, as it does for Chrome, where the Firefox preset had no cap of its own.
- **`1`** (or any other bare non-zero number) keeps its 3.0.0 meaning: exclusive HEADERS priority, and the User-Agent's own PRIORITY frames (none for Chrome, six for Firefox).
- **Pseudo-header order** from part 4 replaces the User-Agent's guess. `roundTripper.RoundTrip` sets fhttp's `PHeader-Order:` key from the fingerprint just before sending, so it applies to every caller (`Do`, the v1 dispatcher, the v2 handler, `NewTransportWithHTTP2Fingerprint`) without touching `utils.go`.
- `String()` writes the frame list back and keeps the settings separator it was parsed with.

```js
// Node
await cycleTLS.get(url, {
  userAgent: firefoxUA,
  http2Fingerprint: '1:65536;2:0;4:131072;5:16384|12517377|0|m,p,a,s',
});
```

```go
// Go
client.Do(url, cycletls.Options{
    UserAgent:        chromeUA,
    HTTP2Fingerprint: "1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p",
}, "GET")
```

##### Behaviour changes to know about

- A string with a frame list no longer sets the exclusive bit on HEADERS (it did only because `Sscanf` read the first stream ID as a flag). Use `http2Priority` to set it.
- Part 3 `0` with a Firefox User-Agent no longer sends six PRIORITY frames.
- Part 4 now has an effect, and a non-empty part 4 that is not a permutation of `m,a,s,p` is an error. An order that left one out would make fhttp drop that pseudo-header and send a broken request.
- Settings and window values are parsed strictly. `1:65536abc` was accepted by `Sscanf` and is now an error.

##### Tests

`http2_wire_test.go` starts a local TLS listener that speaks HTTP/2 with a raw `golang.org/x/net/http2` framer and records SETTINGS, the connection WINDOW_UPDATE, PRIORITY frames, the HEADERS stream ID and priority, and the pseudo-header order. Requests go through `Do`.

- `TestHTTP2FingerprintREADMEExampleOnWire` (Chrome and Firefox User-Agent): SETTINGS `1:65536,4:131072,5:16384`, window 12517377, six PRIORITY frames with wire weights 200, 100, 0, 0, 0, 240, first stream 15, order `m,p,a,s`. Both subtests failed before.
- `TestHTTP2FingerprintChromeStyleOnWire`: `1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p` gives those four settings, window 15663105, no PRIORITY frames, stream 1, order `m,a,s,p`. The Firefox subtest failed before; the Chrome subtest passed and guards against regressions.
- `TestHTTP2FingerprintPseudoHeaderOrderOnWire`: a Safari-style string with a Chrome User-Agent sends `m,s,a,p`. Failed before.
- `TestHTTP2FingerprintLegacyExclusiveFlagOnWire` and `TestHTTP2DefaultsUnchangedOnWire` passed before and after: bare `1` and requests without a fingerprint send the same frames as 3.0.0.
- `http2_priority_test.go`: `TestNewHTTP2FingerprintParsesAkamaiFormat`, `...LegacyFlagAndSeparators`, `...RejectsBadInput`, `TestHTTP2FingerprintApplyFirefoxNoPriorityFrames`. New API or new errors, so they could not pass before.

##### Left out

- New default fingerprints. Without `http2Fingerprint`, fhttp's presets still decide the bytes, and they are older than current Chrome and Firefox. Changing defaults for every HTTP/2 user is not a patch-release change.
- An `InitialStreamID` field in fhttp would replace the Navigator switch. The fork cannot be changed from this repository.
- The expected values for real browsers come from tls-client's profiles. They were not checked against a browser capture.

#### 2. `http2Priority`

##### What was wrong

With `http2Fingerprint` set, the HEADERS frame always carried weight 256 (wire 255), dependency 0, and exclusive only for a bare `1`. Without it, HEADERS carried no priority at all. Neither could be changed, so Chrome (exclusive, weight 256), Firefox (weight 42) and Safari (no priority) could not all be matched.

##### What changed

`http2.go`: type `HTTP2PriorityOptions` with `UnmarshalJSON`, `MarshalJSON`, `priorityParam`, `key`; function `applyHTTP2Priority`, called from `roundTripper.configureHTTP2Transport`.

```go
type HTTP2PriorityOptions struct {
    Weight    int    `json:"weight"`    // RFC 7540 weight 1-256; 0 means 256. Wire byte is Weight-1.
    Exclusive bool   `json:"exclusive"`
    StreamDep uint32 `json:"streamDep"` // 0 means none
    Disabled  bool   `json:"-"`         // JSON false sets it
}
```

| `http2Priority` | HEADERS frame |
|---|---|
| absent or `null` | as 3.0.0: weight 256 with a fingerprint, no priority without one |
| `{"weight":42,"exclusive":false,"streamDep":0}` | those values |
| `false` | no priority fields |
| `true` | read as `{}`: weight 256, not exclusive |

Weight uses the same scale as the fingerprint's priority entries: the number a browser trace shows, one more than the wire byte. A weight outside 1-256 is refused when the JSON is decoded, and from Go when the HTTP/2 transport is built.

The option works without `http2Fingerprint`. In that case only the HEADERS priority changes; SETTINGS, WINDOW_UPDATE and the browser's PRIORITY frames stay as the preset sends them.

```js
// Chrome
{ http2Fingerprint: '1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p',
  http2Priority: { weight: 256, exclusive: true, streamDep: 0 } }
// Safari
{ http2Fingerprint: '2:0;3:100;4:2097152;9:1|10420225|0|m,s,a,p', http2Priority: false }
```

```go
cycletls.Options{HTTP2Priority: &cycletls.HTTP2PriorityOptions{Weight: 42}}
cycletls.Options{HTTP2Priority: &cycletls.HTTP2PriorityOptions{Disabled: true}}
```

##### Tests

`http2_priority_test.go`, against the same local HTTP/2 server:

- `TestHTTP2PriorityOptionOnWire`: eight cases. Exclusive 256, weight 42, zero weight, a stream dependency on top of the README frame list, `false` with a fingerprint, the option without a fingerprint for Chrome and Firefox, and `false` without a fingerprint. Each asserts the HEADERS priority, the PRIORITY frames and the stream ID.
- `TestHTTP2PriorityInvalidWeightFailsRequest`, `TestHTTP2PriorityJSON` (object, `false`, `null`, absent, bad values, marshalling), `TestClientKeyCoversHTTP2PriorityAndProxyHeaders`.

These use the new field, so they did not compile before.

##### Left out

The Node types. Another change adds `http2Priority` and `proxyHeaders` to the TypeScript options; the JSON shape above is what the Go side reads.

#### 3. HTTP/3 ignored the proxy

##### What was wrong

`proxy` together with `forceHTTP3` or `protocol: "http3"` sent the request straight from the machine's own address. The HTTP/3 branch of `roundTripper.RoundTrip` never used `rt.dialer`, and `http3Dial` opened a plain UDP socket. Run against a local UDP listener with a proxy configured, the unchanged code delivered 16 QUIC packets to the target.

##### What changed

The request now fails with `ErrHTTP3ProxyUnsupported` before a socket is opened. There is no fallback to a direct connection and none to TCP.

- `http3.go`: `ErrHTTP3ProxyUnsupported`, `roundTripper.usesProxy`.
- `roundtripper.go`, `RoundTrip`: the first thing the HTTP/3 branch does is return the error when the dialer is not `proxy.Direct`. This covers every caller, including the v2 handler and a custom dialer passed to `NewTransportWithProxy`.
- `index.go`, `dispatchHTTP3Request`: a check at the top returns the error through `fullRequest.err`, which the dispatcher turns into an error frame, before a client is built.
- `index.go`, `Do`: returns the error as a Go `error`. Without this, `Do` would wrap it into a `Response` with a status code like other transport failures.

The message is `cycletls: HTTP/3 cannot be sent through a proxy; remove the proxy or drop forceHTTP3/protocol "http3"`. Go callers can test for it with `errors.Is`.

`Do` only treats `ForceHTTP3` as HTTP/3; it never read `Protocol`. A `Do` call with `Protocol: "http3"` and a proxy goes over TCP through the proxy, as before, so nothing leaks there.

##### Tests

`http3_fixes_test.go`, `TestHTTP3WithProxyReturnsErrorAndSendsNoPackets`: a local UDP listener counts datagrams while the request is made three ways (`processRequest` with `forceHTTP3` and with `protocol: "http3"`, `Do`, and a `roundTripper` with a proxy dialer). Each must return `ErrHTTP3ProxyUnsupported`, and the listener must have seen zero packets. All four parts failed before.

##### Left out

HTTP/3 through a proxy. It needs SOCKS5 UDP ASSOCIATE or CONNECT-UDP (MASQUE), a new client and a `net.PacketConn` wrapper, and few proxies offer either.

#### 4. HTTP/3 small fixes

##### What was wrong

- `headerOrder` with HTTP/3 failed every request. `RoundTrip` puts fhttp's `Header-Order:` key in the header map; quic-go checks header names and answered `http3: invalid http header name "Header-Order:"`. Confirmed by running, not only by reading.
- `insecureSkipVerify` was ignored on HTTP/3. A self-signed server gave status 495.

##### What changed

- `http3.go`, `http3RequestHeader`: copies the headers for quic-go without `Header-Order:` and `PHeader-Order:`. `makeHTTP3RequestWithTransport` in `roundtripper.go` uses it. The caller's header map is not modified.
- `InsecureSkipVerify` is set on the TLS config in `ghttp3Dial` and `uhttp3Dial` (`http3.go`) and in `makeHTTP3Request` (`roundtripper.go`), which builds the config for later dials on the same transport.

`headerOrder` does not order headers on HTTP/3. quic-go writes the header map in Go's map order and has no option for it. The fix makes the request succeed; it does not add ordering.

##### Tests

`http3_fixes_test.go`, against a local quic-go `http3.Server` with a self-signed certificate:

- `TestHTTP3InsecureSkipVerifyOption`: 200 with the option, refused without it. Failed before (495).
- `TestHTTP3HeaderOrderDoesNotBreakRequest`: sets `Browser.TLSConfig` to skip verification, which already worked, so that before the fix it failed for the header reason alone. Asserts the server saw the request headers and no ordering key.
- `TestHTTP3HeaderOrderThroughDo`: the same through `Do` with both options. Failed before.

##### Left out

Header order, pseudo-header order and SETTINGS order on HTTP/3. They need a forked or replaced HTTP/3 stack.

#### 5. `quicFingerprint`

##### What was wrong

The option did nothing for HTTP/3 and something wrong for TCP. `dialTLS` was its only reader: when set, it built the TCP ClientHello from `QUICStringToSpec`, which ignores the string beyond a length check and offers ALPN `h3`. A local TLS listener saw `[h3 h3-29 h3-28 h3-27]` from a plain HTTPS request, which no TCP server speaks.

On the HTTP/3 side nothing fills `Browser.USpec` from the option, and even with `USpec` set from Go the uquic connection is closed and quic-go dials again without it.

##### What changed

`quicFingerprint` is now a no-op, and says so.

- `roundtripper.go`: removed the `QUICFingerprint` branch from `dialTLS` and the matching case from `retryWithTLS13CompatibleCurves`. TCP requests pick their ClientHello from `ja3`, `ja4r` or the User-Agent as if the option were absent.
- `http3.go`, `logQUICFingerprintNoOp`: called from `newRoundTripper`, writes one debug-log line when the option is set: `quicFingerprint is set but has no effect: HTTP/3 requests use quic-go's own QUIC Initial, and TCP requests ignore it`.

The option is still accepted and still part of the client pool key, so existing calls keep working.

##### Tests

`TestQUICFingerprintLeavesTCPClientHelloAlone` in `http3_fixes_test.go`: a local TLS listener records the ALPN list of a request made with `quicFingerprint`. It must be `[h2 http/1.1]`. Failed before with the `h3` list.

##### Left out

Wiring `USpec` through to uquic, so that the QUIC Initial packet really changes. It is not small. quic-go's `http3.Transport` cannot take a uquic connection, so it means moving HTTP/3 requests to uquic's own `http3` package, an old quic-go fork with different types and without request trailers. uquic's last tag (v0.0.6) only has Chrome 115 and Firefox 116 parrots, and the brief ruled out bumping it. The existing `USpec` path (`uhttp3Dial`, then a second plain dial in `makeHTTP3Request`) is unchanged.

`QUICStringToSpec` and `CreateUQuicSpecFromFingerprint` stay in `utils.go`; nothing on the request path calls them now. The README still lists `quicFingerprint` as "QUIC fingerprint" and should say it has no effect yet.

#### 6. `proxyHeaders`

##### What was wrong

There was no way to add headers to the CONNECT request. Proxy providers use them for session, country and sticky-IP control. `connectDialer` had a `DefaultHeader` map and a context hook (`ContextKeyHeader`), and nothing set either from options.

##### What changed

- `connect.go`: `setProxyHeaders` copies the option into `connectDialer.DefaultHeader`; `proxyHeadersKey` feeds the pool key. `createNewClient` in `client.go` calls `setProxyHeaders` right after it builds the dialer.
- Header names keep the casing given. A header with the same name as a default (`User-Agent`, and `Proxy-Authorization` from the proxy URL's credentials) replaces it, whatever the casing.
- The headers go only on the CONNECT request, for `http://` and `https://` proxies, over HTTP/1.1 or HTTP/2. They are not sent to the target. SOCKS proxies have no CONNECT request, so the option does nothing there.
- Request `headers` are not sent to the proxy, as before.

```js
{ proxy: 'http://user:pass@proxy.example:8080',
  proxyHeaders: { 'X-Proxy-Session': 'abc123', 'X-Proxy-Country': 'de' } }
```

```go
cycletls.Options{
    Proxy:        "http://user:pass@proxy.example:8080",
    ProxyHeaders: map[string]string{"X-Proxy-Session": "abc123"},
}
```

##### Tests

`connect_proxy_headers_test.go`: a local TCP listener records the raw CONNECT request, answers 200, then plays the origin inside the tunnel and records that request too.

- `TestProxyHeadersSentOnConnect`: the headers are on CONNECT with their casing, the defaults are still there, the request's own headers are not on CONNECT, and the proxy headers are not on the tunnelled request.
- `TestProxyHeadersOverrideDefaults`: one `user-agent` and one `Proxy-Authorization` line, with the caller's values.
- `TestNoProxyHeadersLeavesConnectUnchanged`: without the option the CONNECT request is byte-for-byte what 3.0.0 sent. Passed before and after.
- `TestProxyHeadersJSONAndSocks`: JSON decoding, `browserFromOptions`, and that SOCKS dialers are left alone.

##### Left out

- A test against an HTTPS proxy that negotiates HTTP/2. The headers travel in the same `DefaultHeader` map on that path; it was read, not run.
- Multi-value proxy headers. The option is `map[string]string`, one value per name.
- The proxy's response headers and body on a failed CONNECT are still not returned to the caller.

#### Shared plumbing

Both new options are threaded the same way:

- `types.go`: two fields at the end of `Options`.
- `client.go`: two fields on `Browser`; `generateClientKey` adds both to the pool key, so clients that differ only in these options do not share connections; one line in `createNewClient`.
- `index.go`: `browserFromOptions` and the `Browser` literal in `Do` copy both fields.
- `roundtripper.go`: `roundTripper.HTTP2Priority` plus the cached parsed fingerprint; `newRoundTripper` copies the field.

### impl-go-dispatch: Go request dispatch fixes

Eight faults in the Go side of request dispatch, found in 3.0.0 and fixed on `impl/3.0.1-go-dispatch`. Each section says what was wrong and how it was shown, what changed, how it is tested, what a user will notice, and what was left out.

The shipped binary is built from `src/index.go`, which only registers `cycletls.WSEndpoint`. `main()` in `cycletls/index.go` never runs.

The probe scripts named below drive the built binary through the Node clients against local servers. "Before" is `origin/version/3.0.1` at `a19d74f`; "after" is this branch. The Go tests live in `cycletls/go_dispatch_test.go`, `cycletls/go_dispatch_ws_idle_test.go` and `cycletls/state/debug_logger_test.go`. They use `httptest` servers and call the dispatchers directly, on both the legacy path (`processRequest` + `dispatcherAsync`) and the V2 path (`processRequestV2` + `dispatcherAsyncV2`). None needs the network.

To show each test fails without the fix, `go_dispatch_test.go` was copied into an untouched export of the base branch and run there. Every test in it failed. The tests in the other two files name variables and fields that did not exist before, so they cannot compile on the base branch; for those the "before" evidence is the probe.

#### New names

| Name | Kind | Meaning |
|---|---|---|
| `CYCLETLS_DEBUG` | environment variable | Set to anything but empty, `0`, `false`, `off` or `no` to get DEBUG lines on stdout |
| `state.DebugEnvVar`, `state.DebugEnabled()` | Go, exported | The variable's name and its parsed value |
| `Response.HeaderValues` | Go field, `map[string][]string`, JSON `headerValues` | Every value of each response header from `Do` |
| `WebSocketClient.UseProxyDialer(proxy.ContextDialer)` | Go method, exported | Send the WebSocket through a proxy dialer |
| `WebSocketClient.ConnectContext(ctx, url)` | Go method, exported | `Connect` with a context that can stop the handshake |
| `SSEClient.ConnectRequest(req, timeout)` | Go method, exported | Open an event stream with a request the caller built |
| `wsPingInterval`, `wsIdleTimeout` | package variables, unexported | 30 s and 90 s. See item 3 |

No option was added to `Options`.

#### 1. Bad input killed the Go process

**What was wrong.** `processRequest`, `dispatchHTTP3Request`, `dispatchSSERequest` and `dispatchWebSocketRequest` called `log.Fatal` when the client or the request could not be built. An unknown proxy scheme, a proxy URL with no host, a bad method or a bad URL ended the process, and with it every other request. Node's restart check looks for `panic` or `fatal error` on stderr, and `log.Fatal` prints neither, so nothing restarted.

`fatal.js`, before:

```
"2_bad_proxy_scheme": "rejected \"Request timeout after 4000ms\" in 4002ms",
"pidAfter": "none (process gone)",
"3_good_again": "rejected \"Request timeout after 4000ms\" in 4003ms"
```

After:

```
"2_bad_proxy_scheme": "resolved status=400 data=\"failed to create HTTP client: scheme ftp is not supported\" in 0ms",
"pidAfter": "70119",   (same pid as before the bad request)
"3_good_again": "resolved status=200 data={\"ok\":true} in 1ms"
```

**What changed.** In `cycletls/index.go` the seven `log.Fatal` calls on the request path now return `fullRequest{options, err}` through a new helper, `requestError`. Both dispatchers already turned `res.err` into an error frame with status 400. An eighth `log.Fatal` in `WSEndpoint`, reached by a plain HTTP request to the port, is now a log line.

A search of `cycletls/` and `src/*.go` for `log.Fatal` and `panic(` found two more places. `src/index.go` calls `log.Fatal` when the listener fails to start, which is correct. `flow_control.go` panics on a negative credit value, which cannot be reached because credits arrive as unsigned 32-bit numbers.

A panic while a request is being built was the other way to die: `readSocket` builds requests on a goroutine with no `recover`. `safeProcessRequest` now wraps the build on both paths and turns a panic into a request error.

The early error returns also cancel the context they had created. `go vet` had been flagging three of them.

**Tests.** `TestBadInputReturnsErrorFrame`: for each path and each of plain HTTP, SSE, WebSocket and HTTP/3, a bad proxy scheme, a proxy with no host, a bad URL and a bad method each give exactly one error frame, and a good request afterwards still succeeds. On the base branch this test ends the test binary.

**What a user notices.** A request with bad options now fails by itself with status 400 and a message. On the legacy client it resolves with that status, as other Go-side errors do.

#### 2. One bad request poisoned the legacy connection

**What was wrong.** `Options.UnmarshalJSON` takes a string or an array of strings as a header value. For anything else (`headers: { 'x-int': 1 }`) the decode failed, `readSocket` logged it and returned, and the handler left the socket open with nobody reading it. Node went on writing requests into it and each one timed out.

`poison.js`, before:

```
"2_number_header": "rejected \"Request timeout after 4000ms\" in 4001ms",
"3_good_again": "rejected \"Request timeout after 4000ms\" in 4002ms",
```

After:

```
"2_number_header": "resolved status=400 in 1ms",
"3_good_again": "resolved status=200 in 0ms",
```

**What changed.** In `readSocket` (`cycletls/index.go`), a message whose options do not decode is answered with an error frame, `invalid request options: ...`, addressed to the `requestId` read from the raw JSON, and the loop carries on. A message that is not JSON at all has no request ID to answer, so it is logged and skipped. The legacy handler in `WSEndpoint` now closes its socket when it finishes.

**Tests.** `TestLegacySocketSurvivesBadRequest` opens a real `?v=1` socket to `WSEndpoint`, sends a non-JSON message, a request with a numeric header value, then a good request, and expects an error frame for the bad one and a full response for the good one. On the base branch it times out with no frames at all.

**What a user notices.** The request with the bad value fails at once; the client keeps working.

**Left out.** Go still rejects a numeric header value rather than turning it into a string. The Node agent does that conversion before sending. The fourth line of `poison.js`, `timeout: -1`, is a Node-side fault and is unchanged.

#### 3. A WebSocket silent for 30 seconds was destroyed

**What was wrong.** Both WebSocket loops set a 30 s read deadline before each read and treated the timeout as "try again". gorilla/websocket does not allow that: after any read error the connection is failed for good.

- Legacy path: the loop retried at once, and gorilla panics on the thousandth read of a failed connection. The reader goroutine had no `recover`, so the process died.
- V2 path: the reader goroutine exited after the timeout, the main loop saw the timeout and went round again, found the channel closed and returned without sending `ws_close` or `end`.

`wsidle.js` (upstream sends nothing for 41 s), before:

```
"upstreamClosed": ["30.1s upstream saw close code=1006", "30.2s upstream saw close code=1006"],
"legacyStdio": ["30.1s ... restarting in 500ms (attempt 1 of 3) -> panic: repeated read on failed websocket connection"],
"v2ReadyStateAfter": 1, "legacyReadyStateAfter": 1, "v2send": "ok"
```

After:

```
"upstreamClosed": [],
"legacyStdio": [],
"v2ReadyStateAfter": 1, "legacyReadyStateAfter": 1, "v2send": "ok"
```

Writing the test also showed that the legacy path never sent `end` after the upstream closed. Nothing closed `closeChan`, so `dispatchWebSocketAsync` waited for a cancel that never came and kept its goroutines and the connection.

**What changed.**

- New file `cycletls/ws_upstream.go`. `upstreamWatch` replaces the read deadline. Reads now block with no deadline. A goroutine pings the upstream every `wsPingInterval` (30 s) when nothing has arrived for half that time. Any message, ping or pong counts as a sign of life. Only when nothing at all has arrived for `wsIdleTimeout` (90 s) does it close the connection, which wakes the reader. Both are package variables so a test can shorten them. A `wsPingInterval` of zero or less turns pings and the idle check off.
- `dispatchWebSocketAsync` (legacy, `index.go`): the reader never reads again after an error. Whichever goroutine stops first ends the connection; the main routine closes the socket, waits for both goroutines, and sends `end`. The client gets one `ws_close`, with the server's own close code if it sent a close frame, or 1006 and the reason otherwise. The dispatcher also stops when the client's own socket to the Go process closes.
- `dispatchWebSocketAsyncV2` (`ws_handler_v2.go`): same watch, and every way the reader can end now sends `ws_close` then `end`. A failed write to the upstream sends `ws_error`, `ws_close` 1006 and `end` where it used to send `ws_error` and carry on.
- A read that ends the connection no longer sends `ws_error`. Both Node clients emit `'error'` for that frame, and an `'error'` event with no listener throws in Node. `ws_close` with code 1006 carries the same news.

**Tests.** `TestSilentWebSocketSurvivesIdleWindow` shortens the windows to 50 ms and 600 ms, connects to a server that answers pings and sends nothing, waits two idle windows, and expects only `response` and `ws_open`, with at least one ping seen upstream. Then the server closes, once with close code 4001 and once by dropping the TCP connection, and the test expects `ws_close` (4001 or 1006) followed by `end`. `TestDeadWebSocketIsClosedAfterIdleWindow` uses a server that never answers pings and expects `ws_close` 1006 and `end` after the idle window, not before. Both run on both paths.

**What a user notices.** A quiet feed stays connected. When the upstream goes away, the socket object gets `close` with the real code. The upstream now receives a ping about every 30 s while it is quiet. A close code other than 1000 or 1001 used to arrive as an error event; it now arrives as a close event with that code.

**Left out.**

- Browsers do not send WebSocket pings, so a server could tell this client from a browser by them. They only go out on a quiet connection, and the interval is a variable, but there is no option to turn them off from a request.
- `send()` on the Node side still reports success after the upstream is gone until the close frame arrives. That check is in the TypeScript clients.
- The V2 control socket between Node and Go has its own 30 s pong deadline with a 27 s ping period (`pongWait`, `pingPeriod`), and every V2 request ends after `requestTimeout`, two hours. Neither was touched.

#### 4. V2 SSE dropped the caller's headers, and SSE was GET-only

**What was wrong.** `dispatchSSERequest` put the caller's headers into the `SSEClient` and built a bare placeholder request. `dispatchSSEAsyncV2` sent the placeholder, so the server got no caller headers, no `Accept` and no User-Agent. The legacy path used `SSEClient.ConnectWithTimeout`, which did send the headers but hard-coded GET with no body. Confirmed by reading; there is no probe. On the base branch the new test shows it:

```
method = "GET", want POST
body = "", want the caller's body
header Authorization = [], want ["Bearer token-1"]
header Accept = [], want ["text/event-stream"]
```

**What changed.** `dispatchSSERequest` builds the request with `buildHTTPRequest`, the function plain HTTP requests use, so headers, header order, method, body and User-Agent are all carried. `withSSEAccept` adds `Accept: text/event-stream` before the build, so it takes its place in the header order, unless the caller sent a non-empty `Accept` in any letter case. In `cycletls/sse.go`, `SSEClient.ConnectRequest` sends a prepared request; `Connect` and `ConnectWithTimeout` now build their GET and call it. The legacy dispatcher calls `ConnectRequest` with the built request, so both paths send the same thing.

V2 SSE and HTTP/3 requests were registered in the request tracker and never removed. `dispatcherAsyncV2` now removes them, and `processRequestV2` cancels SSE, HTTP/3 and WebSocket requests when the client's socket closes, so a stream blocked on a quiet upstream no longer outlives its client.

**Tests.** `TestSSERequestCarriesHeadersMethodAndBody` sends a POST with a body, three headers and a User-Agent on both paths and checks what the server received, including the default `Accept`. `TestSSECallerAcceptWins` sends `accept`, `Accept` and `ACCEPT` and expects exactly one `Accept` header with the caller's value, and GET when no method is given.

**What a user notices.** Authorization and other headers reach SSE endpoints from the default client. POST event streams work.

**Left out.** The legacy path still fails any reply that is not status 200 with `text/event-stream`, and still does not decode a compressed stream; V2 does neither check and does decode.

#### 5. `enableConnectionReuse` read as false when left out

**What was wrong.** The field is a plain `bool`. The comments and the README say reuse is the default, but a JSON request that left the field out decoded to `false`. The default-export Node client never sets it, so every one of its requests built a client, opened a connection and closed it.

**What changed.** `Options.UnmarshalJSON` (`cycletls/types.go`) shadows the field with a `*bool`. Absent or `null` means true. An explicit `false` is still honoured.

**Decision on Go `Do`.** The struct zero value was not changed. A `bool` cannot tell "left out" from `false`, and making the field a `*bool` would break every caller that writes `EnableConnectionReuse: true`. So a Go caller who builds `Options` as a struct literal still gets reuse off unless they set the field. A comment in `Do` now says so.

**Tests.** `TestEnableConnectionReuseJSONDefault` decodes `{}`, `null`, `true` and `false`, alone and inside a request, and checks the struct zero value is still false. `TestJSONRequestsReuseConnectionByDefault` sends four JSON requests with the field left out to a TLS server and expects one connection; the base branch opens four. The connection-close tests added in 3.0.0 (`connection_close_test.go`) set the field in struct literals and still pass.

**What a user notices.** The default Node client keeps connections open between requests to the same host with the same fingerprint, proxy and cookies. Requests get faster and the server sees fewer handshakes. Pass `enableConnectionReuse: false` for a fresh connection per request.

#### 6. WebSocket requests ignored `proxy`

**What was wrong.** `dispatchWebSocketRequest` never read `Options.Proxy`. `NewWebSocketClient` dials with gorilla and `http.ProxyFromEnvironment`, so a WebSocket request with `proxy` set left from the caller's own address. `userAgent` and `cookies` were dropped too. On the base branch the new test reports:

```
proxy saw 0 connections, want 1: the WebSocket did not use it
User-Agent = "Go-http-client/1.1", want the userAgent option
Cookie = "theme=dark", want the header and the cookies option joined
```

**What changed.**

- `WebSocketClient.UseProxyDialer` (`cycletls/websocket.go`) sets gorilla's `NetDialContext` to a proxy dialer and clears the environment proxy. `dispatchWebSocketRequest` builds that dialer with `newConnectDialer`, the function the HTTP path uses, so HTTP, HTTPS and SOCKS proxies all work, with the same `proxyInsecureSkipVerify` rule. `connect.go` was read, not edited. A proxy URL that cannot be used fails the request. A proxy that refuses the tunnel fails it too; there is no fallback to a direct connection.
- When the proxy speaks HTTP/2, the tunnel is one stream of a shared connection. `noDeadlineConn` drops deadlines on that tunnel, because a write deadline left by one WebSocket control frame would fail the proxy connection's later writes.
- `webSocketHandshakeHeaders` (`ws_upstream.go`) adds `User-Agent` from `userAgent` when the caller sent no such header, and adds the `cookies` option to any `Cookie` header.
- The handshake uses `ConnectContext`, so cancelling the request stops it.

**Tests.** `TestWebSocketUsesProxy`, on both paths: `ws://` through an HTTP CONNECT proxy, `wss://` through the same, and `wss://` through an HTTPS proxy that answers CONNECT over HTTP/2. Each checks the proxy saw one connection for the upstream, a message arrived through it, and the upstream received the User-Agent, the joined Cookie header and a custom header. `TestWebSocketProxyFailureDoesNotDialDirect` uses a proxy that answers 403 and checks the upstream was never reached.

**What a user notices.** `proxy` on `ws()` is honoured. The handshake carries the configured User-Agent in place of `Go-http-client/1.1`.

**Not done.** The WebSocket TLS handshake is still Go's stock `crypto/tls`. `ja3`, `ja4r`, `http2Fingerprint` and `headerOrder` do not reach it. That needs a uTLS handshake in gorilla's `NetDialTLSContext` with ALPN forced to `http/1.1`, and it was out of scope. With no `proxy` set, the WebSocket still follows `HTTP_PROXY` and `HTTPS_PROXY` from the environment, as before. SOCKS proxies go through the same dialer but have no test here.

#### 7. Go `Do` gaps

**What was wrong.**

- `Do` built its `Browser` without `ServerName`, `DisableGrease` and `TLS13AutoRetry`, which `browserFromOptions` does pass. The SNI override and exact JA4R matching did not work through `Do`.
- `Do` called `DecompressBody`, which reads only the first `Content-Encoding` value and has no zstd.
- `Response.Headers` is `map[string]string` and kept only the first value of each header.

On the base branch:

```
gzip_then_br: body not decoded: got 101 bytes, want 18023
zstd:         body not decoded: got 56 bytes, want 18023
server saw SNI "", want the ServerName option
```

**What changed**, all in `Do` (`cycletls/index.go`) apart from the new field:

- The three missing fields were added to the `Browser` literal. The literal was kept, not swapped for `browserFromOptions`, because two other 3.0.1 branches add fields there.
- `decodeBufferedBody` runs the body through `newDecodedBody`, the streaming decoder in `content_decoding.go` that the dispatchers use. It undoes every coding in the header, in reverse order, and knows gzip, deflate, br and zstd. The decoded size is capped at 64 MiB with the existing `readLimited`. `utils.go` was not edited and `DecompressBody` is still there for other callers.
- When the body decodes, `Content-Encoding` and `Content-Length` are removed from the response headers, since they described the compressed bytes. When it does not decode, or would pass the cap, the body and headers come back as received, as before.
- `Response.HeaderValues` holds every value. `Headers` is unchanged.

**Tests.** `TestDoDecodesEveryContentEncoding` (gzip, `gzip, br`, zstd, `GZip`), `TestDoLeavesUndecodableBodyAlone`, `TestDoSendsServerName` (a TLS server records the SNI it was sent) and `TestDoKeepsEveryResponseHeaderValue`.

**What a user notices.** A Go caller gets zstd and multi-coded bodies decoded. `Response.Headers` no longer lists `Content-Encoding` or `Content-Length` for a body that was decoded; a caller that decoded zstd by hand after checking that header will now find it absent and the body already plain. `ServerName` takes effect.

**Left out.** `DisableGrease` and `TLS13AutoRetry` are passed through but have no test of their own here. `Do` still ignores `Protocol`, still leaves `PHeader-Order` handling as it was, and still reports a failed request as a `Response` with a nil error. `Queue`, `RespChan` and `RespChanV2` are still not wired up.

#### 8. Debug output was always on

**What was wrong.** `state.DebugLogger` wrote to stdout always: 372 bytes for each V2 request. The default Node client spawned the Go process with piped stdio and never read it. When the 64 KB pipe filled, Go blocked inside the next `debugLogger.Printf`.

`pipeprobe2.js`, before and after:

```
default client, unread server stdout: 240/1500 requests ok in 5355ms; first failure: Request timeout
default client, unread server stdout: 1500/1500 requests ok in 1186ms; first failure: none
```

**What changed.** In `cycletls/state/globals.go` the logger writes to `io.Discard` unless `CYCLETLS_DEBUG` is set when the process starts. Go's logger skips formatting when its output is `io.Discard`, so the calls cost almost nothing.

**Does anything read those lines?** No. The legacy Node client (`src/index.ts`, the child's `stdout` listener) prints stdout to the console unless a chunk contains `WS_AUTH_TOKEN=`. It does not parse a token out of stdout: it makes the token itself and passes it to the child in the environment. The only Go code that prints `WS_AUTH_TOKEN=` is the `main()` in `cycletls/index.go` that never runs. The default client does not read stdout at all.

**Tests.** `TestDebugOutputFollowsEnv` and `TestDebugLoggerSilentByDefault` in `cycletls/state/debug_logger_test.go`.

**What a user notices.** The legacy client no longer prints `DEBUG:` lines to the console. To get them back, set `CYCLETLS_DEBUG=1` in the environment of the Node process; the child inherits it.

**Left out.** Lines written with the standard `log` package still go to stderr: bad-message reports, the client-creation failure in V2, and the tracker clean-up notes. They are rare, and a parent that never reads stderr could in theory still fill that pipe. The TypeScript side drains both pipes in its own branch.

### impl-node-v2: the default Node client

This covers the client you get from `new CycleTLS()` (the default export, in `src/flow-control-client.ts`), its wire protocol (`src/protocol.ts`) and the Go packet reader (`cycletls/packet_reader.go`). The legacy `initCycleTLS` client is not part of it.

Every "before" result below was produced on this branch before the change, on macOS arm64 with Node 22.18 and Go 1.26.11, against local HTTP and WebSocket servers only. The probe scripts are `pipeprobe2.js` and `bigbody.js` from the gap research, plus `startprobe.js` written for this work.

#### 1. The client stopped answering after about 240 requests

##### What was wrong

`startServer` spawned the Go server with piped stdout and stderr and never read either pipe. The Go server writes debug lines to stdout on every request, about 372 bytes each by the gap research's count. A pipe holds 64 KB. Once it was full, the server blocked inside its next log write and no request got an answer.

Probe, before:

```
default client, unread server stdout: 240/1500 requests ok in 5667ms; first failure: Request timeout
```

After:

```
default client, unread server stdout: 1500/1500 requests ok in 756ms; first failure: none
```

##### What changed

`startServer` now spawns with `stdio: ["ignore", "pipe", "pipe"]` and attaches a `data` listener to both pipes, so they are always read. With `debug: true` each chunk is printed with a `[CycleTLS server]` prefix; otherwise stdout is dropped. The last 2000 characters of stderr are kept and added to the error when the server fails to start.

The pipes stay open, so a later change can still read a line from the server (an auth token, a ready line). Nothing is parsed from them today.

This holds whether or not the Go logger is silenced: the test below runs against a binary that still logs on every request.

##### Test

`tests/v2-lifecycle.test.js`, "500 sequential GETs complete". Before the change it failed at request 240.

#### 2. A request over 64 KB crashed Node

##### What was wrong

`buildInitPacket` wrote the whole options JSON, body included, behind a 16-bit length. Anything over 65535 bytes threw. The throw happened inside a WebSocket `open` listener, outside the promise, so Node died with an uncaught exception. Binary bodies travel as base64 inside the same JSON, so they hit the limit near 48 KB.

Probe, before:

```
"post60k": "status 200, server got 60000 bytes",
"uncaughtException": "String byte length 100087 exceeds maximum 65535 for protocol encoding"
```

After:

```
"post60k": "status 200, server got 60000 bytes",
"post100k": "status 200, server got 100000 bytes"
```

##### The new packet: `init2`

There are now two packets that start a request. They carry the same fields and differ only in the width of one length. All integers are big-endian.

| Field | `init` | `init2` |
|---|---|---|
| request id | u16 length, then bytes | u16 length, then bytes |
| method name | u16 length, then `init` | u16 length, then `init2` |
| initial window | u32 | u32 |
| options JSON | **u16** length, then bytes | **u32** length, then bytes |

Nothing may follow the options JSON in either packet.

The client sends `init` when the options JSON is 65535 bytes or less and `init2` when it is longer. Small requests therefore still work against a Go binary older than 3.0.1. The Go reader accepts both, so a client older than 3.0.1 works against the new binary.

The options JSON of `init2` may be at most 32 MiB (33554432 bytes). Both sides enforce it: `MAX_INIT_OPTIONS_BYTES` in `src/protocol.ts` and `MaxInitOptionsLen` in `cycletls/packet_reader.go`. That allows a text body of about 32 MiB or a binary body of about 24 MiB. The Go reader checks the declared length before it reads the field.

##### What changed

- `src/protocol.ts`: `buildInitPacket` picks the packet by size and throws `InitPacketTooLargeError` above the limit. New exports: `MAX_INIT_OPTIONS_BYTES`, `InitPacketTooLargeError`.
- `src/flow-control-client.ts`: the new `encodeInit` builds the packet at the top of `request()`, `ws()` and `sse()`, before any connection is opened. Those methods are `async`, so a failure there rejects the returned promise. An over-limit request rejects with `CycleTLSError`, status 413, message `Request too large: the encoded request is N bytes, the limit is 33554432 bytes (32 MiB) including the body`. A body that is over the limit by its length alone is refused before it is copied into a JSON string. Any other encoding failure (a circular object in `headers`, for example) rejects with `CycleTLSError`, status 400, `Failed to encode request: …`. The new `sendInit` routes a failed `send` into the same rejection path.
- `cycletls/packet_reader.go`: `parseInitMessage` accepts `init` and `init2`. New: `readLongBytes`, `MaxInitOptionsLen`, `ErrInitOptionsTooLarge`.
- `cycletls/ws_handler_v2.go`: not edited. `readInitPacketV2` already hands the whole message to `parseInitMessage`.

##### Tests

- Go, `cycletls/packet_init2_test.go`: `init2` with bodies from empty to 8 MB; the old `init` still parses; both packets decode the same options to the same request; a declared length over the limit fails with `ErrInitOptionsTooLarge`; truncated, trailing-byte, bad-JSON, bad-window and unknown-method packets fail; a 16-bit layout sent under the name `init2`, and the reverse, fail.
- Jest, `tests/v2-large-body.test.js`: packet choice at exactly 65535 and 65536 bytes; 100 KB POST; 1 MB text body with multi-byte characters, byte-exact; 1 MB and 8 MB random binary bodies, byte-exact; three over-limit cases and one unencodable case reject; no uncaught exception or unhandled rejection was seen and the client still works afterwards.

#### 3. Starting and stopping the server

Each finding was confirmed by running `startprobe.js` before any change.

| Finding | Before | After |
|---|---|---|
| A probe connection for every request | `one request opened 2 WebSocket connections`, every time | Two for the first request, one for each later request |
| Concurrent first requests | `10 first requests -> 10 spawns` | `10 first requests -> 1 spawns` |
| Start budget fixed at 5 s | Server that needs 6 s: `rejected after 5166ms: Server failed to start` | `ok 200 after 6273ms` |
| Path with a space | `rejected: Server failed to start` | `ok 200` |
| Node exits without `close()` | `go server pid 37159 alive: true` | `alive: false` |
| SIGINT, SIGTERM | Node keeps running, Go server alive | Go server killed. See below for Node itself |

##### What changed, all in `src/flow-control-client.ts`

**One shared startup.** `ensureServerRunning` keeps the startup in `startPromise`. Calls that arrive while it is pending wait on the same promise. Once a server has answered, `serverReady` is set and later calls return at once with no probe. `serverReady` is cleared when the spawned server exits, and when a request cannot connect. In the second case the new `openSocket` runs the check again, which starts a server, and connects once more, so a request made after the server died still succeeds.

**Configurable start time.** New client option `startupTimeout`, in milliseconds, default 20000 (it was a fixed 5000). `startServer` polls from 20 ms up to 100 ms apart until the server accepts a connection. It stops early when the process cannot be spawned or exits, and says why: `CycleTLS server exited during startup (code 3, signal null, port 39511); server output: cannot bind port`. At the deadline it kills the process and rejects with `CycleTLS server did not accept connections on port N within Mms (startupTimeout)`. If the server exits because another process took the port first and that process is a working server, the client uses it, as it did before.

**No shell.** The server is spawned with `shell: false`. The path reaches the OS as one argument, so spaces and shell characters are safe, and the child is the server itself, not a shell around it.

**Cleanup at exit.** While a client owns a live server, the module listens for `exit`, `SIGINT` and `SIGTERM` on `process` and kills the server in each. The listeners are added when the first server starts and removed when the last one is gone, so importing the package installs nothing. `exit` also covers `process.exit()` and an uncaught exception.

**Signals are passed on.** After killing the servers the signal handler removes itself. If no other listener for that signal is left, it sends the signal to its own process again, so the process ends by that signal exactly as it would without CycleTLS. If the application has its own listener, the application decides.

**`close()` waits.** `close()` now resolves after the server process has exited (or after 2 s). It also settles a startup that is still in flight, so a server cannot appear just after `close()` returns. A client can be used again after `close()`; the next request starts a new server.

##### One part is not fixed here: SIGINT through the package entry point

`src/index.ts` registers the legacy client's SIGINT and SIGTERM listeners when the package is imported, and those listeners return without ending the process. Because they are always present, the default client sees another listener and does not re-send the signal. Result today, measured:

```
signal SIGINT: node STILL RUNNING (signal swallowed); go server pid 75833 alive: false
```

The Go server is now killed, but a script that only idles still needs a second Ctrl-C. With the client module loaded alone the process ends by the signal (tested). `src/index.ts` belongs to the legacy-client work; the fix there is to re-send the signal after cleanup when no other listener is left, or to stop registering at import. That change was left to the legacy-client work on purpose.

##### Tests

`tests/v2-lifecycle.test.js`: one spawn for 10 concurrent first requests (spawn spy); `shell: false`; the child is gone when `close()` resolves; a request after `close()` and a request after the server was killed both start a new server; a path with a space; one connection per request after the first; a server that takes 6 s to start; `startupTimeout` reached; a server that exits at startup; a missing executable.

`tests/v2-exit-cleanup.test.js` runs `tests/v2-fixture-child.js` in a child Node process: `process.exit()` without `close()`; an uncaught exception; SIGINT and SIGTERM with the client module alone (the process must end by that signal and the server must be gone); SIGINT with an application listener (the application's exit code wins, the server is gone); SIGINT and SIGTERM through the package entry point (the server is gone).

The shell scripts and signals make three lifecycle tests and the signal tests POSIX only; they are skipped on Windows.

#### 4. `require('cycletls')` lacked three names

##### What was wrong

`src/index.ts` ends with `module.exports = CycleTLS`, which replaces the object the named exports were put on, and then re-adds names by hand. `CycleTLSError`, `CreditManager` and `Protocol` were not re-added. Probe, before: `CreditManager: undefined`, `Protocol: undefined`, and the same for `CycleTLSError`. After: `function`, `function`, `object`.

##### What changed

`src/index.ts`, two places: the import next to the existing `import CycleTLS from "./flow-control-client"` now also brings in `CycleTLSError` (as `CycleTLSErrorV2`, because that file has a local interface of the same name), `CreditManager` and `Protocol`; and three `module.exports.…` lines were added to the CommonJS block. Nothing else in that file was touched.

##### Test

`tests/v2-exports.test.js`: the three names exist and work, the older names are unchanged, and every value named in an `export { … }` or `export * as` line of `dist/index.d.ts` exists on the required module.

#### 5. `timeout: -1` failed at once

##### What was wrong

The client passed the timeout straight to `setTimeout`, which fires a negative delay after 1 ms. The Go server reads a negative timeout as "no timeout" (`cycletls/request_timeout.go`). Probe, before: `timeout -1: rejected after 2ms: Request timeout`. After: `timeout -1: ok 200 after 1505ms` against an endpoint that answers after 1.5 s.

##### What changed

`normalizeTimeout` in `src/flow-control-client.ts` now decides, for the per-request option and the client option alike:

| Value | Meaning |
|---|---|
| negative | no timeout: no client timer, and `-1` is sent to Go |
| `0` | the default, 30000 ms, which is what Go does with 0 |
| above 2147483647, or `Infinity` | no timeout (a Node timer cannot hold it and would fire at once) |
| not a number | the client's default |
| anything else | that many milliseconds |

The value sent to Go is rounded up to a whole number, because Go decodes it into an integer and a fraction made the whole request fail to parse.

The same rule applies to `ws()` and `sse()`.

##### Test

`tests/v2-timeout.test.js`: a table for `normalizeTimeout`; `-1`, `0` and `Infinity` against an endpoint that takes 1.5 s; a 300 ms timeout still rejects with status 408; a client created with `timeout: -1`.

#### 6. Options were forwarded by a hand-written list

##### What was wrong

`request()` copied 23 named fields into the object sent to Go. `ws()` and `sse()` each copied 14. Any option not named was dropped without a word, so `serverName`, `http2Fingerprint`, `cookies` and others never reached Go from `ws()` or `sse()`, and a new option would have reached Go from nowhere.

##### What changed

`src/flow-control-client.ts` now has two exported lists: `FORWARDED_REQUEST_OPTIONS` (sent to Go under the same name) and `CLIENT_ONLY_REQUEST_OPTIONS` (`readTimeout`, `sseTimeout`). A type check beside them fails the build when `RequestOptions` has a key that is in neither list. `buildWireOptions` copies every listed option that is set and is used by all three methods.

New fields on `RequestOptions`, all forwarded: `tlsProfile` (string), `shuffleExtensions` (boolean), `clientHello` (hex string), `sessionResumption` (boolean), `caCerts` (PEM strings), `certPins` (strings), `http2Priority` (`{ weight?, exclusive?, streamDep? }` or `false`), `proxyHeaders` (string to string), and two that Go already had: `proxyInsecureSkipVerify` and `protocol`.

`ws()` forces `method: "GET"`, an empty body and `protocol: "websocket"`. `sse()` forces `protocol: "sse"` and adds its `Accept` and `Cache-Control` headers under the caller's.

##### Test

`tests/v2-forwarded-options.test.js`: the keys of `RequestOptions`, read from the source file, equal the two lists together; a stand-in WebSocket server records the init packet and the test compares the JSON with what was passed, for `request()`, `ws()` and `sse()`, with a value for every forwarded option.

#### 7. `port: 0` never worked

##### What was wrong

The client kept port 0 and passed `WS_PORT=0` to the Go server, which then listened on a random port. The client went on dialling port 0, so no request could succeed, and each attempt started another server. Probe (`port0.js`), before:

```
port 0, request 1: rejected (5160ms): Server failed to start
port 0, request 2: rejected (5157ms): Server failed to start
spawns: [{"pid":84837,"port":"0"},{"pid":84857,"port":"0"}]
go processes alive after close(): 1 of 2
```

After:

```
port 0, request 1: ok 200 (38ms)
port 0, request 2: ok 200 (1ms)
spawns: [{"pid":85896,"port":"51043"}]
go processes alive after close(): 0 of 1
```

##### What changed

`port: 0` now means "a free port". On the first request `connectOrStart` asks the OS for one (`pickFreePort`: listen on 0, read the port, close), keeps it for the life of the client and starts the server on it. No probe runs first, since there is no known port to probe.

The constructor now throws a `RangeError` for a port that is not an integer from 0 to 65535, and for `port: 0` with `autoSpawn: false`, where there is no server to place. A numeric string is still accepted.

Another process can take the port between the pick and the server's bind. The server then exits and the request rejects with the startup error from item 3. This was not seen in any run.

##### Test

`tests/v2-lifecycle.test.js`, "port: 0": five concurrent requests and one more use one server on a non-zero port; two clients get two servers on different ports, closing one leaves the other working, and none is left after both close; the two constructor errors.

#### 8. The `tlsfingerprint` suites killed each other's server

##### What was wrong

All four `tests/tlsfingerprint/*.test.ts` suites built the default client on port 9119. Jest runs them in parallel workers, so they shared one Go server, owned by whichever worker won the port. When that worker closed its client, the server died under the requests the other three had in flight. Seen once here before the fix: 5 tests failed with `CycleTLSError: Connection closed`, one run out of three.

##### What changed

Each suite now passes `port: 0`, so every client gets its own server on its own free port. This was chosen over fixed per-suite ports because fixed ports can still collide with another checkout running the same suites on the same machine.

The client's own rule is unchanged and was already the safe one: `close()` only kills a server that this client spawned.

##### Test

`npm test -- --testPathPattern=tlsfingerprint --forceExit`, without `--runInBand`, three runs in a row: 43 passed and 2 skipped each time, exit 0.

#### What you will notice

- Long-running processes keep working past 240 requests.
- Bodies up to about 32 MiB of text or 24 MiB of binary can be sent. Above that the promise rejects with status 413.
- A request that cannot be encoded rejects its promise. It no longer ends the process.
- The first request is slightly faster and later requests open one local connection, not two.
- A slow machine gets 20 s for the server to start, and `startupTimeout` changes that. A server that cannot start fails at once with the server's own message; before, it failed after 5 s with `Server failed to start`.
- The Go server is gone when Node exits, however it exits, short of `SIGKILL`.
- `await client.close()` returns only when the server process has exited.
- `timeout: -1` waits for as long as it takes. `timeout: 0` means 30 s; it used to fail at once.
- With `debug: true` the server's log lines are printed, prefixed `[CycleTLS server]`.
- `ws()` and `sse()` now send every option you pass, among them `cookies`, `serverName`, `headerOrder`, `http2Fingerprint` and `enableConnectionReuse`. Whether Go acts on each of them for WebSockets and SSE is a separate matter on the Go side.
- An install path with a space works.
- `port: 0` gives the client its own server on a free port. An invalid port throws when the client is created.

#### Left out, and why

- **SIGINT through the package entry point** still needs a second Ctrl-C when the application has no listener. The cause is in `src/index.ts`, described under item 3.
- **`SIGKILL` of Node** still orphans the Go server. Node gets no chance to run anything. Fixing it needs the server to notice that its parent is gone (a closed stdin, for example), which is a change to the Go entry point.
- **Request bodies are still sent in one packet**, so the whole body is in memory on both sides, several times over at the peak. 32 MiB keeps that bounded. Larger uploads need a streamed request body, which is a new set of packets and belongs in a minor release.
- **No read limit on the server's WebSocket.** The Go reader rejects a declared options length over 32 MiB, but gorilla has already buffered the message by then. Setting `SetReadLimit` means editing `handleWSRequestV2`, which another change owns.
- **No auth token is sent.** The shipped binary does not check one today. If that is switched on, the default client has to send the token in `dial` and `testConnection`.
- **`enableConnectionReuse` and `tls13AutoRetry` defaults** are unchanged: an omitted value still reaches Go as false.
- **README**: `startupTimeout`, the body limit and the timeout rule are not in the README yet.
- **Windows** was not run. The spawn options were already shell-free there; `close()` still uses `taskkill /t /f` and then a direct kill.

### impl-node-legacy: the legacy Node client (`initCycleTLS`) and the Jest setup

This covers the changes to `src/index.ts`, the option types of both Node clients, and the non-fingerprint Jest job. Each section says what was wrong, what changed, how it is tested, and what a user will notice.

"Run" means I ran it on macOS arm64 with Node against the binary built from this branch. "Read" means I read the code and did not run it.

#### 1. The client never recovered when the Go process died

**What was wrong.** `SharedInstance` had no `exit` listener on the child process and no `close` listener on the control WebSocket. A restart only happened when stderr matched `panic|fatal error|runtime error|address already in use`. A process killed by a signal, by the OOM killer or by `log.Fatal` writes none of those.

Run, before the change (`crashprobe.js`: init, one request, `SIGKILL` the Go process, two more requests):

```
1_before:                 resolved status=200 in 4ms
serverListeningAfterKill: no (not respawned)
2_after_sigkill:          rejected "Request timeout after 4000ms" in 4002ms
3_after_sigkill_again:    rejected "Request timeout after 4000ms" in 4000ms
```

After the change the same probe prints `yes (respawned)` and both later requests resolve with 200.

**What changed.**

- `handleSpawn` listens for the child's `close` event, and for `exit` with a 250 ms fallback timer. `close` fires after stderr has been read, so a fatal line (for example "address already in use") is still handled by the stderr path first and keeps its own rules. Both lead to the new `handleChildExit`, which ignores an exit we asked for (shutdown, a child already replaced, a failed initialization) and passes any other exit to `handleFatalError`.
- `handleFatalError` is the restart mechanism added for issue 428 and is unchanged in its limits: 3 restarts in a row, delays of 500, 1000 and 2000 ms, a fresh set after 30 s of healthy running, no restart on "address already in use". There is no second mechanism. The one addition: after initialization it calls `handleConnectionLost` before deciding on a restart.
- `handleConnectionLost` (new) drops the dead socket, rejects everything in flight, and reconnects through the same code as initialization: the host calls `createClient` and waits for its restarted child; a client that was sharing another process's server calls `checkSpawnedInstance`, so it becomes the host when the port turns out to be free. The reconnect is bounded by the init `timeout` (default 20 s) and by the respawn limit. It reads the auth token on each attempt, so it picks up the token of the restarted child.
- `createClient` now registers a `close` listener on the socket once it is open, which calls `handleConnectionLost`. This covers a socket that closes while the process stays alive.
- Each `CycleTLSClientImpl` keeps a `pending` map from request id to a function that fails that request. `SharedInstance.failInFlight` calls them. A request waiting for headers rejects. A buffered response whose body is still arriving rejects. A `responseType: 'stream'` response has its stream destroyed with the error. A WebSocket from `ws()` gets a `close` event with code 1006.
- `sendRequest` checks that the socket is open and throws at once when it is not. While a reconnect is running the message is `CycleTLS is reconnecting to its Go process after it stopped; retry the request shortly`.
- When the reconnect fails for good, later requests reject with `CycleTLS lost its Go process and could not reconnect (<reason>). Call exit() and initCycleTLS() again.` `InstanceManager.getOrCreateSharedInstance` no longer hands back such an instance: a new `initCycleTLS()` on the same port starts a new process. `removeSharedInstance` takes the instance as a second argument so an old client's `exit()` cannot remove the new instance.
- `cleanup()` and `exit()` set the shutdown flag before killing the child, so that exit is never treated as a crash. They also settle requests still in flight.

**Tests.** `tests/legacy-crash-recovery.test.js` uses the real binary and kills its process group with `SIGKILL`:

- two requests in flight (one with `timeout: -1`) reject with an `Error` naming the Go process, a later request succeeds, and exactly one restart happened;
- a request made while the process is away rejects in under a second with the "reconnecting" message, not after its 30 s timeout;
- a buffered body and a stream body that are mid-transfer both fail with an error;
- after `exit()` the pending request rejects and no new process is spawned.

`tests/legacy-reconnect.test.js` uses a fake child and a local `WebSocketServer` (the pattern from `tests/respawn-limit.test.js`):

- the socket closes while the process stays alive: the in-flight request rejects, the client reconnects, no respawn;
- the server goes away for good: requests reject with "reconnecting", then with "could not reconnect"; a new `initCycleTLS()` spawns again and survives the old client's `exit()`;
- a child that exits with no stderr output is restarted 3 times and no more.

All of these fail on the unchanged source (run). `tests/respawn-limit.test.js` still passes unchanged.

**What a user will notice.** Requests in flight when the process dies now reject within milliseconds with an `Error` instead of timing out. Requests during the restart window (about 0.6 s for a first crash) reject at once and should be retried. A stream response emits `error` on its stream; a stream with no `error` listener will throw, as any Node stream does. The log line `Fatal error detected ..., restarting in 500ms (attempt 1 of 3) -> Go process exited unexpectedly (signal SIGKILL)` appears for exits that used to be silent. `exit()` now rejects requests that were still in flight; before, they sat until their timeout.

#### 2. Init rejections were strings

**What was wrong.** `SharedInstance.rejectInitialization(reason: string)` and the connection timeout in `createClient` rejected with plain strings. `initCycleTLS` wrapped them, so the public API already threw an `Error`; only callers of the internal `_InstanceManager` saw a string (read).

**What changed.** `rejectInitialization` accepts an `Error` or a string and always rejects with an `Error`. The timeout path rejects with `new Error(...)`. The `reject` parameters are typed `(reason: Error) => void`. `initCycleTLS` keeps its message (`Failed to initialize CycleTLS: <message>`) and sets the original error as `cause`.

**Tests.** `tests/instanceManager.test.ts` matched with `rejects.toMatch`, which only works on strings. It now asserts `rejects.toBeInstanceOf(Error)` and `rejects.toThrow(/Executable not found|not found/i)`. With the unchanged source those two assertions fail.

**What a user will notice.** Nothing through `initCycleTLS`. Code that used `_InstanceManager` directly and compared the rejection to a string must read `.message`.

#### 3. Non-string header values poisoned the connection

**What was wrong.** Run, before the change (`poison.js`):

```
1_good:          resolved status=200 in 7ms
2_number_header: rejected "Request timeout after 4000ms" in 4003ms
3_good_again:    rejected "Request timeout after 4000ms" in 4002ms
```

The Go `Options.UnmarshalJSON` accepts a string or a string array per header. A number fails decoding, and the Go handler stops reading that socket without closing it, so every later request goes unanswered (read; the Go half is fixed by another change).

**What changed.** `normalizeRequestHeaders` runs at the start of every request and `ws()` call (from `applyDefaultOptions`). Strings pass through; numbers, booleans and bigints go through `String()`; arrays are converted element by element and stay arrays, so `string[]` multi-value headers work as before. `undefined`, `null`, objects, functions and nested arrays throw a `TypeError` that names the header, before anything is sent. The option type is now `RequestHeaders` (`string | number | boolean`, or an array of those); response headers keep the `HttpHeaders` type.

`sendRequest` also rejects a `body` that is not a string after the `URLSearchParams` and `FormData` conversions. An object body poisoned the connection the same way (issue 337).

**Tests.** `tests/legacy-headers.test.js`, real binary and a local HTTP server that records `rawHeaders`: number, float, zero, boolean and bigint values arrive as strings; `["one", 2, true]` arrives as three header lines; an object, `undefined`, `null`, an array holding an object and a nested array each reject with a `TypeError` in under a second, nothing reaches the server, and the next request works; an object body rejects and the next request works. All fail on the unchanged source.

**What a user will notice.** `headers: { 'x-int': 1 }` works. A bad value fails that one request with a clear message instead of freezing the client.

#### 4. Timeouts

**What was wrong.** `timeout: -1` rejected in 1 ms with `Request timeout after -1000ms` (run, `poison.js`), because the timer was set to `options.timeout * 1000`. The Go side treats a negative timeout as "no timeout" (`cycletls/request_timeout.go`).

The client timer is cleared when the headers arrive, and Go bounds only the wait for headers. I confirmed by running that a stalled body is unbounded: against a local server that sends headers and one chunk and then nothing, a request with `timeout: 1` was still pending after 3 s. That check is kept as a test.

**What changed.**

- A negative `timeout` sets no client timer. `0` or unset still means 30 s.
- New opt-in `readTimeout` in milliseconds. It starts when the headers arrive and restarts on every body chunk, so it measures idle time. When it fires the request fails with `Read timeout: no response data for <n>ms` (a buffered request rejects, a stream response emits `error`) and the request is cancelled in the Go process. It is not sent to Go. `timeout` on this client is in seconds and `readTimeout` in milliseconds; the name and unit match the default client's `readTimeout`.

**Tests.** `tests/legacy-timeout.test.js`, real binary and a local server: `timeout: -1` resolves; `timeout: -1` waits for headers that `timeout: 1` gives up on; a stalled body without `readTimeout` stays pending; `readTimeout: 400` rejects a buffered request and errors a stream after delivering the first chunk; a body that drips for longer than `readTimeout` in total, but with no long gap, completes. Five of the seven fail on the unchanged source; the two that pass there are the stalled-body check and a plain request.

**What a user will notice.** `timeout: -1` works. Nothing else changes unless `readTimeout` is set.

#### 5. Types and docs for the 3.0.1 options

**What changed.** Added to `CycleTLSRequestOptions` in `src/index.ts`, with doc comments: `tlsProfile`, `clientHello`, `shuffleExtensions`, `sessionResumption`, `caCerts`, `certPins`, `http2Priority` (with an exported `HTTP2Priority` interface), `proxyHeaders`, plus `tls13AutoRetry`, `bodyBytes` and `readTimeout`, which the default client had and this one did not. The comments on `http2Fingerprint`, `quicFingerprint`, `forceHTTP3` and `timeout` were updated.

`certPins` did not exist in either TypeScript type before; it existed only in the Go struct.

The legacy client spreads the options into the JSON it sends, so the new fields reach Go unchanged. Two exceptions, both deliberate: `bodyBytes` (a `Uint8Array`) is turned into the base64 string Go expects for a `[]byte`, and `readTimeout` is removed. When `tlsProfile` or `clientHello` is set the client no longer adds its default JA3; before, a default JA3 was added whenever no fingerprint option was present.

The same eight new fields were added to `RequestOptions` in `src/flow-control-client.ts`, in one marked block at the end of the interface. That file belongs to another change. I added types only: the default client builds its request field by field, and forwarding the new fields is not done here.

README has a new section "New in 3.0.1" before "Usage", with the option table, the precedence order and the behaviour changes, including `proxy` with `forceHTTP3` now returning an error and `enableConnectionReuse` left out now meaning true. #### Left out, and why

- **Signal handling (`SIGINT`/`SIGTERM` swallowed by the import-time listener in `src/index.ts`).** The author of the default-client change asked for the legacy handler to re-send the signal after cleanup. That is gap G21, marked "needs care", and was not in this brief. Not done.
- **Forwarding the new options in the default client.** Types only, see section 5.
- **Waiting for the reconnect inside a request.** A request made while the Go process is restarting fails at once. Making it wait would hide the crash from the caller but needs its own bound against the request timeout. The error says to retry.
- **`Buffer` or `FormData` with binary parts as `body`.** `FormData` is still read as UTF-8 text. Use `bodyBytes` for binary data.
- **Other options with the wrong type** (for example `timeout: "5"` or `timeout: 0.5`, which Go cannot decode into an int). These still depend on the Go-side fix that answers a decode error with an error frame.
- **The 13 skipped suites and the two other `port: 0` suites.** They belong to the default client.
- **Windows and Linux runs.** Not available here.

### Conflicts and how they were settled

## Not done in 3.0.1

Found by the research or the implementation agents and left for a later release.

**Fingerprint defaults**
- The Go default ClientHello imitates Chrome 133; the legacy Node default pairs a Firefox JA3 with a Chrome 101 User-Agent. Changing either changes every user's wire output.
- Default HTTP/2 settings are older than current Chrome and Firefox.
- `tlsProfile` stops at Chrome 133, Firefox 120 and Safari 16.0, the newest in utls v1.8.2. Newer ones need a utls release or hand-written specs.
- The JA3 path sends Firefox signature algorithms under a Chrome User-Agent.
- No default header set or header order per browser.

**Protocol gaps**
- `quicFingerprint` has no effect. HTTP/3 has no fingerprint control and cannot use a proxy.
- WebSocket handshakes carry Go's TLS fingerprint, not the requested one. `certPins` cannot be checked on WebSocket or HTTP/3, so both refuse.
- Real ECH, TLS 1.3 0-RTT, client certificates.
- Upstream WebSocket pings are sent to a quiet connection; browsers do not send them, and there is no switch.

**Client and server**
- The shipped Go binary does not switch on the WebSocket auth token, rate limiter or concurrency cap.
- The first Ctrl-C through `require('cycletls')` is swallowed by the legacy client's import-time handler. The Go child is killed; Node keeps running.
- A Node process killed with SIGKILL leaves its Go server running.
- Request bodies travel as one packet, held in memory on both sides, up to 32 MiB.
- The Go `Queue` and `RespChan` API described in the README is empty.

**Features peers have**
- Request retries, response metadata (protocol, remote address, timings), local address binding, IPv4-only dialing, cookie dump and restore, racing HTTP/3 against HTTP/2.

**Known bugs not fixed**
- A JA3 string whose version field is 769 or 773 panics inside utls.
- With `timeout` set, the legacy Node client sometimes rejects and sometimes resolves with a 408, depending on which timer fires first.
